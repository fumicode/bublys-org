# バブリの組み合わせ

**ひとつのことだけをうまくやる小さな部品を、人が自由に組み合わせて、自分専用の道具を組み立てる。**
そのために何を足すかを決めた設計。2026-09-30 の議論の結果。

まだ実装の途中なので、ここに書いてあることは**決めたこと**であって、
全部が動いているという意味ではない。進み具合は最後の節に書く。

---

## 0. なぜ要るか ── 反例がある

旅程・地図・アクティビティの 3 つは、互いを直接 import して繋がっていた。

```
旅程   → 地図の selectSpots / setRoute、アクティビティの selectActivities
アクティビティ → 地図の selectSearchBounds / selectSpots
```

依存の向きは一方通行で、その意味では「正しい」。
しかし**部品としては成立していない**:

- **旅程だけを選ぶことができない。** 地図とアクティビティが無いとビルドも通らない
- **旅程にタスクやメモを落としても何も起きない。** 受け取れる型が 2 つに決め打ちだから。
  「10:00-11:00 にこのタスクをやる」は旅程の本来の仕事のはずなのに
- 組み合わせる相手を**作者が決めてしまっている**。組み立てているのが人ではない

> **向きが正しいことと、部品として独立していることは別**。

これは 1 つのアプリを 3 ファイルに割っただけで、バブリが 3 つあるのとは違う。

---

## 1. 通り道はひとつ

> **バブリどうしの通り道は「ものを渡すこと」だけ。他のバブリの引き出しは覗かない。**

引き出し（Redux の slice）を直接読むと、読む側が相手の名前を知ってしまう。
渡すだけにすれば、受け取る側は「何が来たか」しか知らなくてよい。

この規則だけで、上の 3 か所の名指しが全部なくなる。

### 既にある前例

変換エディタ（`object-transformer-libs`）が既にこのやり方をしている
（`MappingEditorFeature.tsx` の `resolveDropped`）:

1. 荷物からドラッグ型を取る
2. `getSchema(型名)` で**形**を引く（`domain-registry` の登録簿）
3. 値は `application/json` から読む

持ち主を 1 つも import していない。**繋ぎ方の見本はここにある。**

---

## 2. 渡されたものを、どう読むか

### 役（やく）

受け取る側は、来たものが何なのかを知らない。知らないまま使えるように、
**型は自分の項目に「役」を名乗る**。

最初に置く役は 4 つ:

| 役 | 意味 |
|---|---|
| 題名 | そのものを一言で呼ぶ名前 |
| 時間 | かかる長さ（分） |
| 金額 | 費用（円） |
| 場所 | 緯度経度、またはそれを持つものの id |

旅程は「時間の役を名乗っている項目」を探す。`durationMin` という**綴りには頼らない**。
綴りに頼ると、タスクが `estimateMinutes` だったときに**黙って繋がらない**
（繋がらなかったことが誰にも見えないのがいちばん悪い）。

### 役を足してよいとき

> **2 つ以上のバブリが、独立にその役を要ったとき。**
> 1 つのバブリのためだけの役は、役ではなく**そのバブリの中の事情**。

これが無いと、バブリが増えるたびに「予約できる」「写真がある」「評価がある」と
共通語彙が膨らんで、最後は誰も全体を言えなくなる。

### 何も名乗っていなくても落ちる

> **受け取る側が要求してよいのは、題名だけ。**

旅程に何を落としても**必ず予定になる**（既定 60 分・費用なし）。
役を名乗っていれば、そのぶんうまくやる。名乗っていなければ既定になるだけ。

下限を下げておかないと、「対応している型」の一覧が生まれて、
また作者が組み合わせを決めることになる。

### 足りない道具：持ち主に聞く口

`ObjectView` が荷物に載せているのは型・url・ラベルだけで、**中身を載せていない**。
だから受け取った側は url しか持てず、値を読むには持ち主を import するしかなかった
（これが 0 節の名指しの構造的な理由）。

2 つの案があった:

- **A：荷物に中身も載せる。** 小さいが、渡した瞬間の写しなので、あとで元を直しても追随しない
- **B：「この型の、この id は何か」を引ける登録簿を足す。** 毎回持ち主に聞けるので古くならない

**B を採る。** `registerObjectUrl` / `registerObjectIdentity` が既にある並びなので素直だし、
地図で地点の名前を直したときに旅程の予定が古いままにならない
（いまの実装がわざわざ持ち主に聞いているのは、まさにその良さのため）。

## 3. 場所を名乗るものは、地図に出る

最初は「地点は地図が持つ」と決めていたが、**これだと地図は自分の `Spot` しか描けない**。

> **地図は、場所の役を名乗っているものなら何でもピンにする。**

`Spot` は「それ自体で存在する場所」という型の 1 つになるだけ。
宿もアクティビティも予定も、場所を名乗れば地図に出る。

同じ理由で、**旅程がその日の道を地図の引き出しに書き込むのもやめる**。
道が要るなら、**その日を掴んで地図に落とす**。範囲で絞りたいなら、
**範囲を掴んで一覧に落とす**。どちらも「渡す」に揃う。

---

## 4. 口（くち）── できることを差し出す

ものを渡すだけでは足りない場面がある。

> 例：地図の検索欄は普段は地名でしか探せないが、
> スポットのバブリを繋ぐとスポットでも探せるようになる。

これは**データを渡す話ではなく、できることを差し出す話**。
ホストは「ここに穴が空いている」と名乗り、別の泡がそこに入る。

### 口は 2 種類

|  | **集まる口** | **座る口** |
|---|---|---|
| 何人居られるか | 何人でも | 1 人だけ |
| 繋ぐと | 答え手が増える（アップグレード） | 前に座っていた者と替わる（置き換え） |
| 相手が描くか | **描かない。ものを返すだけ** | 描く |
| 例 | 探す・候補を出す | この行をどう描くか |

**置き換えを特別扱いにしない**ためにこう分けた。
「足すのか替えるのか」をユーザーに毎回選ばせると手数が増えるし、
機械に選ばせると優先度の数字か読み込み順になる ── どちらも「人が組み立てる」から遠い。

口のほうが最初から性質を名乗っていれば、**人がやることはどちらも「掴んで落とす」だけ**で済む。
そして置き換えの危なさが**座る口の中だけに閉じる**。

### 既定は自分が持つ

> **穴を開けてよいのは、自分でも答えを 1 つ持っている所だけ。**

地図は自分で地名検索ができる。その上に増える。
何も繋がなくても成り立つから、繋いだ泡を外しても**既定に戻るだけ**で壊れない。

答えを持っていない穴を作ると、そのバブリは単体で意味を持てなくなる。

### 口の名前は「動詞 × 役」

| 口 | 動詞 | 役 |
|---|---|---|
| 地図の検索欄 | 探す | 場所 |
| 旅程の「予定を足す」候補 | 候補を出す | 予定になれるもの |
| 旅程の 1 行の描き方 | 描く | 予定 |

**動詞は少数の閉じた集合**（探す・候補を出す・描く）。**役は 2 節と同じ語彙**。

つまり **伸びるのは役だけ**。渡すデータの意味も、口の契約も、同じ 1 つの語彙で書く
── 仕組みを 2 つ作らない。

### 箱は場が配る

「集まる口」は**ものを返すだけ**なので、箱の話が出ない。
ホストが自分の流儀で結果を描く。

「座る口」だけは相手が描く。そこは既にある決まりをそのまま使う
（`BubbleBoxContext`）:

> **場が測って箱を配る。中身は配られた箱で姿を決める。**

ポケットも世界線の泡もこれで動いていて、小さい箱を配られるとアイコンになる。
ホストは「これだけの広さです」としか言わないので、**相手の見た目までは決めない**。

## 5. 繋ぐのは人の操作

> **両方ロードしただけでは繋がらない。人が繋ぐ。**

自動で繋がると、組み合わせを決めているのは作者になる。

- **繋ぐ**：答え手の泡を掴んで、ホストの口に落とす
- **口は普段見えない**：何かを掴んだ瞬間、受けられる口だけが光る（いまの drop の手ざわりと同じ）
- **外す**：繋ぎの線を掴んで切る。既定に戻る

### 泡どうし（バブリどうしではない）

繋ぎは **（ホストの泡, 口の名前, 答え手の泡）** の 3 つ組。

バブリ単位にすると 1 回繋げば全部の地図に効いて楽だが、
**同じ道具の違う組み立てを並べて比べられない**。
泡どうしなら、地図を 2 つ開いて片方だけスポット検索付き、が作れる。

泡の id は既に世界線に乗っている配置の中に居るので、**繋ぎもそのまま節になる**
── 新しい保存の場所は要らない。

### 世界線に乗る

繋いだ・外した・替えた、が節になる。
**置き換えを最初から入れられるのは、これがあるから**。壊れても巻き戻せる。

## 6. 進め方と、いまどこまで来たか

1. ✅ **役の語彙**と `registerObjectResolver`（B）── 名指しせずに中身を読めるようにする
2. ✅ **3 つから import を外す**（ただし 1 か所だけ残っている。下記）
3. ⬜ **口の仕組み**（集まる口・座る口）、繋ぐ操作、線、世界線
4. ⬜ **地図の検索欄で実際に繋ぐ** ── 例がそのまま動くか確かめる

### 1 と 2 で入ったもの

| | どこ |
|---|---|
| 役（`role`）と、役から値を引く道具 | `domain-registry` の `SchemaShape` / `roles.ts` |
| 指（`ObjectRef`）と、中身を訊く口 | `object-types` の `registerObjectResolver` / `resolveObjectPlain` |
| 渡されたものの中を歩いて場所を拾う | `domain-registry` の `collectPlaces` |
| 知らない型でも荷物の型を読む | `bubbles-ui` の `anyObjectDragType` |

### 実際にこうなった

- **旅程は何でも受ける。** タスクもメモも落とせば予定になる（既定 60 分・費用なし）。
  役を名乗っていれば、時間も金額も場所もそこから取る
- **地図は場所を名乗るものなら何でも描く。** 旅程を落とすと、その中の立ち寄り先が
  書いてある順にピンになり、繋がって道になる。**地図は旅程を知らない**
- 3 つとも、互いの引き出しを覗かなくなった（1 か所を除く）

### まだ残っている名指し

`activity-libs` の `useVisibleActivities` が、いまも地図の引き出し（`selectSearchBounds` /
`selectSpots`）を直に読んでいる。「この範囲で探す」を**渡す**形に直すには、
範囲そのものを掴めるものにするか、口（3 段目）が要る ── そこで一緒に外す。

## 7. まだ決めていないこと

- **動詞をどこまで増やすか。** いまは 3 つ（探す・候補を出す・描く）で始める。
  役と違って閉じた集合のつもりだが、閉じ続けられるかは分からない
- **座る口を置き換えたとき、ホストの他の所が前提にしていたことが崩れないか。**
  「同じ口に座る」ことしか保証していない
- **繋ぎの線をどう描くか。** いまの管（`tube.ts`）は岸の枠の光で、
  泡どうしの関係は描いていない。線は新しく要る
- **繋いだ先の泡が閉じられたら**どうなるか（既定に戻る、でよさそうだが未確定）
- **`place` の役が指す先の型。** いまは指（`{type, id}`）が型を持っているので解決済みだが、
  **その先がさらに指だったとき**は 1 段しか辿っていない（地図の `handedPins`）
- **日をまたぐ予定。** 落としたものが 23 時台に継がれると終わりが翌日になる。
  いまは読むときに 23:59 で止めているだけで、またいだこと自体は表していない
