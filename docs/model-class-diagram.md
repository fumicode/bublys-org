# モデルのクラス図

ドメインモデルの構造を図にするビュー。実装は `bublys-libs/model-graph`、
例は hotel-shift-puzzle（バブル `hotel-shift-puzzle/model-class-diagram`）。

---

## 出どころ — 2つを重ねる。混ぜない

図の中身は2つの出どころから来る。**それぞれ知っている側に聞く**のが要点で、
片方をもう片方から推測しない。

| 何を | どこから | いつ |
|---|---|---|
| クラス・フィールド・メソッド・つながり | **TypeScript のソース**（コンパイラ API で読む） | 生成時 |
| 世界線での所属（live / pinned / external） | **記述子**（`objects/hotelObjects.tsx` の `membership`） | 実行時 |

### なぜソースを読むのか

記述子に `relations` を手で書く案は採らなかった。**モデルを直したときに図だけが黙って
古いまま残る**から。ソースが唯一の出所なら、図は必ずモデルに追従する。

ただし生成物をコミットする以上、生成し直し忘れれば結局同じことが起きる。だから
**古くなったら落ちるテスト**を置いてある（`modelGraph.staleness.test.ts`）。
モデルにフィールドを1つ足すだけで落ちる。

### なぜ所属だけソースから取らないのか

`live` / `pinned` / `external` は**その型が世界線にどう属するか**の宣言で、
クラスの型からは分からない。記述子だけが知っているので、実行時にそこから読む。

登録されていないクラス（集約の中の部品・値オブジェクト）は所属を**描かない**。
「所属が無い」のではなく「所属という概念の対象ではない」ので、
`external` と読ませたら嘘になる。

## 図の読み方

### 配置は2通り。切り替えられる

| | 置き方 | 読めるもの |
|---|---|---|
| **力学**（既定） | つながりの強いものが引き合い、そうでないものは離れる | 関係の**疎密が距離**になる。近い概念が近くに来る |
| 列 | 集約ごとに縦の列。いちばん上が根、下がその中の部品 | 集約の境界がまっすぐ読める。ただし集約の数だけ横に伸びる |

開いた直後は**図全体が窓に収まる倍率**から始まる。「全体」でいつでもそこへ戻せる。
読み方の凡例と申告は**畳んである**（出しっぱなしにすると、ふつうの大きさのバブルでは
説明が窓の半分を占めて図がほとんど見えない）。「読み方」で開く。申告があるときは
そのボタンに `⚠ N` が出る。

**箱はドラッグで動かせる。** 自動配置を捨てずに上から重ねるので、動かしていない箱はそのまま。
「並びを戻す」で自動配置に戻る。動かした位置は**その窓を開いているあいだだけ**覚える
（図の見方の好みであってドメインのデータではないので、世界線には載せない）。

汎用のグラフ配置ライブラリは入れていない。**乱数を使わないため**でもある。
図は「同じ入力なら同じ出力」でなければ、開くたびに配置が変わって前に見た図と比べられない。
初期位置はクラス名のハッシュから決まる。

### 線

| 線 | 意味 |
|---|---|
| ◆ 実線 | **内包**。値やインスタンスを直接持つ＝一緒に保存され、一緒に巻き戻る |
| → 破線 | **id で参照**。集約をまたぐ＝別々に保存され、別々に巻き戻る |

この2つの違いが**集約の境界そのもの**。線の種類で「どこまでが1つのかたまりか」が読める。

線にカーソルを当てると、どのフィールドから来たか・**どうやって見つけたか**が出る。

| 見つけ方 | 意味 |
|---|---|
| 型から | フィールドの型にクラス名が出ている（確実） |
| 命名から | `staffId: string` のような命名から推した（**推測**） |

### 世界線スコープの枠

シアンの破線の枠は**世界線スコープ**。その中は**一緒に保存され、一緒に巻き戻る**。

集約の境界（◆実線）とは**別の軸**。集約は「どこまでが1つのかたまりか」で、
スコープは「どこまでが一緒に巻き戻るか」。ふつうは重なるが、必ずではない。

### 焼き付けメンバーは、外と中の両方に置く

焼き付けメンバー（pinned）は**外の台帳と世界の中の両方に居る**。
片方にしか描くと、どちらかが嘘になる。

| 片方だけ描くと | 消えるもの |
|---|---|
| 枠の中だけ | 外の台帳にも居ること（グローバルの名簿は別に生きている） |
| 枠の外だけ | その世界に載っていること（時間移動しても一緒に付いてくる） |

だから**両方に置いて、点線で結ぶ**。

- 外側は普通の箱（`集約 / pinned ▌`）
- 枠の中は**中身を書かない写し**（`▌Staff`）。もう一度書いても読むものは増えない。
  ただし**幅は本物と同じ**にする。小さくすると脚注のように見えて、
  「世界の中からの矢印が向かう先」として読めない（実際に読めなかった）
- 結ぶ線は**第3の線**。シアンの点線で、両端に四角の印。内包（◆実線・灰）でも
  参照（→破線・黄）でもない——値を持つのでも id で指すのでもなく、
  「世界が生まれた瞬間に同じ参照が焼かれて、以後そちらは動かない」という関係だから

写しは**関係の線を増やさない**。同じオブジェクトなので、つながりは写し元のもの。

### 世界の中からの線は、写しにつなぐ

焼き付けメンバーへ伸びる線は、**どちらの箱に届くかで意味が変わる**。

| 線の出どころ | 届く先 | なぜ |
|---|---|---|
| 世界の**中**に居るもの | 枠の中の写し | 世界の中から見えているのは焼き付けたほう |
| 世界の**外**に居るもの | 外の箱 | 外から見えているのはグローバルの台帳 |

外につなぐと「この世界のものが外を見ている」という嘘になる。hotel では:

```
ShiftAssignment.staffId        → ▌Staff（写し）     勤務表の世界の中
ShiftLeaderRule.leaderStaffIds → ▌Staff（写し）     勤務表の世界の中
ConstraintViolation.staffId    → Staff（外の箱）    どの世界にも属さない
StaffMonthlyShiftWish.staffId  → Staff（外の箱）    external
```

**「世界の中」には集約の部品も入る。** `ShiftAssignment` は記述子に登録されていないが、
`MonthlyStaffSchedule` と一緒に保存され、一緒に巻き戻る。だから枠の中に入るし、
そこから伸びる線も写しに届く。枠が集約の部品まで囲っているのはそのため。

枠も写しも `scopeOf` を注入したときだけ描く。渡さなければ何も描かない。

### 箱

| 枠の色 | 単位 |
|---|---|
| 青（太） | 集約の根。世界線に載り、id で参照される（記述子に登録されている型） |
| 灰 | 集約の中の部品 |
| 緑 | 値オブジェクト（id を持たない） |

右上に「単位 / 所属」。行の先頭の記号でメソッドの種類が分かる。

| 記号 | 意味 |
|---|---|
| `↻`（黄） | **自分を返すメソッド＝更新**。ドメインクラスは不変なので、更新はこの形で現れる |
| `⌂` | static（`of` / `fromPlain` のようなファクトリ） |
| `·` | それ以外（問い合わせ） |

行が多すぎるクラスは省略して「…ほか N 件」と出す。**省略したことが図から分かる形**にしてある。

## 図が申告すること

出せなかったものは黙って消さない。

| 申告 | 意味 |
|---|---|
| state を持たないクラス N 件はフィールドが空 | state オブジェクト規約から外れている型（hotel では制約クラス5件） |
| **参照先を決められなかった id が N 件＝その分だけ線が足りていない** | `〜Id` なのに指す先が決められなかったフィールド |

2つめが要点。推測で近い名前に寄せるより、**決められなかったと言う**ほうが正しい。
ここに出ているぶん、図には線が足りていない。

hotel では4件出る。うち3件（`storeId` / `worldLineNodeId`）は**モデルの外**を指していて、
正しく解けないもの。1件（`linkedReportIds`）は登録名と命名がずれているために解けていない。

## 生成し直す

モデルか記述子を直したら生成し直す。忘れると `modelGraph.staleness.test.ts` が落ちる。

```bash
npm --workspace @bublys-org/model-graph run build
node bublys-libs/model-graph/dist/lib/extract/cli.js \
  --source   hotel-shift-puzzle-bubly/hotel-shift-puzzle-model/src/lib \
  --registry hotel-shift-puzzle-bubly/hotel-shift-puzzle-libs/src/objects/hotelObjects.tsx \
  --out      hotel-shift-puzzle-bubly/hotel-shift-puzzle-libs/src/model-graph/modelGraph.generated.ts
```

集約の根と「登録名 → クラス名」の対応は**記述子のソースから読む**ので、引数に書かない
（`scheduleId` が指すのは登録名 `Schedule`、クラスは `MonthlyStaffSchedule`）。
引数に書くと、型を1つ足したときに黙って古くなる。

## 別のバブリで使う

```tsx
<ClassDiagramView
  graph={MODEL_GRAPH}                        // 生成したもの
  membershipOf={(cls) => /* 記述子から */}    // 省略すると所属を描かない
  scopeOf={(cls) => /* 記述子から */}         // 省略するとスコープの枠を描かない
  mode="force"                                // 'force' | 'column'
  positions={positions}                       // ユーザーが動かした位置
  onMove={move}
  selected={selected}
  onSelect={setSelected}
  scale={scale}
/>
```

`membershipOf` / `scopeOf` を渡さなければ**何も描かない**。知らないことを描かせない。

### スコープの「形」の取り出し方

クラス図は**型の図**なので実体の id が無い。ところが `homeScope` は id を要求する。
hotel では**置き id を渡して形を取り出している**:

```typescript
membership.homeScope("<id>")   // → "Schedule:<id>"
```

ここを手で `"Schedule:<id>"` と書くと、記述子の規約を変えたときに図が古くなる。

## 構造上の約束

| 約束 | なぜ | どう守っているか |
|---|---|---|
| `typescript` を静的 import してよいのは `lib/extract/` だけ | 漏れるとブラウザのバンドルに数MBのコンパイラが入り、Jest（jsdom）からも読めなくなる | 本体のバレルとは**別の入口**（`@bublys-org/model-graph/extract`）にしてある。到達経路は生成コマンドと Node 環境のテストだけ |
| 生成物は手で編集しない | 次の生成で消える | ファイル冒頭に明記。食い違いは staleness テストが落とす |
| つながりの導出は純粋関数 | 「`staffId` は Staff への参照だ」は**判断**で、外すことがある | `domain/relations.ts` に切り出してテストで固定。結果には必ず「どうやって見つけたか」を添える |

## 分かっている限界

- **フィールドの型は文字列**。TypeScript が解決した表示そのままなので、`Record<string, ...>` の
  中身までは図に出ない（カーソルを当てると全文が出る）
- **メソッドは名前と引数名だけ**。引数の意味までは取れない
- **継承・実装を描いていない**。hotel のモデルには無いので、まだ必要になっていない
- 力学配置は総当たり（箱の数の2乗×回数）。21クラスなら一瞬だが、数百クラスでは重くなる
- 動かした位置は窓を閉じると消える。永続はしていない
- 集約が増えるほど図が大きくなる。「全体」と 50% / 75% / 100% の切り替えで凌いでいる
- 同じ部品が2つの集約から内包されている場合、**先に見つけた根に寄せる**（根の名前順で決定的）。
  実際には両方に属しているので、片方の列にしか現れない
