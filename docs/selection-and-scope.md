# 選択とスコープ

> **状態: 決めたが、まだ実装していない。** 議論の結論を残すための文書。

---

## 決めたこと

> **選択はスコープごとに1つ。内側のスコープが勝つ。
> 選択されているものを掴んだら、選択ぜんぶが荷物になる。**

ユーザーから見える「選択」の概念は**1つだけ**にする。実装の中では階層的なスコープを持つ。

---

## なぜ1つにするのか

実装から見ると、いまこのリポジトリには性質の違う「選択」が混ざっている。数えるとこうなった。

| 種類 | 箇所数 | 実態 |
|---|---|---|
| カーソル（いま見ている1つ） | 8 | `selectedXId: string \| null` ＋ `detail = idProp ? byId : selected` が丸ごと同じ形でコピペされている |
| 構えている道具（次の操作の主語・材料） | 4 | event のブラシ、tailor-genie の話者、勤務表のセル、object-transformer の変換元。全部単数 |
| 作業範囲（複数を溜めてコマンドに渡す） | 1 | hotel の `selectedStaffIds` だけ |
| 絞り込み | 6 | 全部チェックボックス → 検索 → URL クエリになって新しいバブルで開く |

**作る側はこの違いを区別できるが、使う側は区別できない。** 3種類の「選ばれている見た目」が同じ画面に並べば、
振る舞いが違うことは伝わらない。

だから概念を1つに畳む。モデルは Finder / ファイルマネージャの選択をそのまま採る。

- 単クリック＝選ぶ
- Shift / Cmd クリック＝足す
- 選んだものがコマンドの対象
- 選んだものをそのままドラッグして持っていく

これで**カーソル・作業範囲・持ち物が1つでまかなえる**。「1つ見る」はサイズ1の選択、
「複数に操作する」はサイズNの選択、「運ぶ」は選択をドラッグすること。

> [click-or-doubleclick.md](./click-or-doubleclick.md) で決めた「単クリックは開かない、ダブルクリックで開く」は、
> Finder モデルの前半にあたる。単クリックが空いているのは、そこに「選ぶ」が入るから。

## スコープ

選択は**階層的なスコープごと**に持つ。

bublys にはすでに階層がある。宇宙は入れ子（[recursive-universe.md](./recursive-universe.md)）で、
世界線も「オブジェクトのかたまりごと」にスコープされる。選択のために新しい構造を作るのではなく、
**同じ階層に乗せる**。

### 内側が勝つ

どのスコープの選択になるかは、**いちばん内側のスコープ**。

これは新しいルールではない。同じ判断をすでに2回している。

- 入れ子の `ObjectView` をダブルクリックすると内側が開く（`stopPropagation`）
- 入れ子の `ObjectView` にホバーすると内側だけ膜が出る（`:has`）

3回目の適用になる。

### 選択の意味はスコープが決める

仕組みは1つ、意味はその場所が決める。

| スコープ | そこでの選択の意味 |
|---|---|
| ガントエディタ | 塗るブラシ |
| 勤務表 | 自動シフトの対象 |
| 会話 | 喋る主語 |
| 宇宙（OS） | 運ぶもの |

「タスクを見たいだけなのにブラシが変わってしまう」は起きない。**見るのはダブルクリック**で、
それは選択を変えないため。

## 格上げと格下げ

### 格上げは自動

**選択されているものを掴んだら、選択ぜんぶが荷物になる。**

「格上げ」という専用の操作は要らない。ドラッグがそのまま格上げになる。
Web でページ内のテキストを選んで外へドラッグすると、それがブラウザの荷物になるのと同じ。

### 格上げは意味を落とす。それでいい

勤務表の中では「自動シフトの対象である3人」。手のひらに乗った瞬間、ただの「3人」になる。
上のスコープは下のドメインを知らないので、落ちるのが正しい。
表からテキストをコピーすると表の構造が落ちるのと同じ。

### 格下げは明示的にだけ

**上がるのはエスカレータ、下りるのは階段。**

手のひらに3人乗っている状態で勤務表バブルを開いても、その3人が自動でコマンドの対象になったりはしない。
下のスコープに入るのは、**そこにドロップしたときだけ**。上から下への自動流入は、
ユーザーが意図しない副作用になる。

## 宇宙に落としたとき

[universe-drop-zone.md](./universe-drop-zone.md) の「誰も受け止めなかったドロップは、宇宙が落ちた場所で受け止める」
を、複数に広げる。

> **1個なら落ちた場所で開く。複数なら手のひらに乗る。**

複数を落として N 個のバブルが一斉に開くと、置き場所も奥行きも決められない。
手のひらは**受け止め先が無かったときの着地点**であり、落とし損ねた荷物が消えないための場所でもある。

## 分けたまま残すもの

1つに畳むのは選択だけ。次の3つは**見た目も置き場も違うので混ざらない**。畳まない。

| | 何か | なぜ混ざらないか |
|---|---|---|
| **ポケット** | 持ち歩く棚 | 選択が「いまこの画面で選んでいるもの」なのに対し、ポケットは永続する。画面を閉じても残り、右下に常設される |
| **絞り込み** | 検索 | すでに URL に凝固する形で解けている。チェックして検索を押すと新しいバブルの URL になり、選択として溜まらない |
| **フォーカス** | キー入力の宛先・最前面 | `focusedBubbleId`。バブルの話であってオブジェクトの話ではない |

## 廃止するもの

**「未選択＝全員」をやめる。**

hotel の `subsetStaff` は「選択が空なら全員、あれば選択者のみ」になっている
（`feature/ScheduleGrid.tsx:239-246`）。これは選択ではなくフィルタの振る舞いで、Finder モデルとは両立しない。

実害も出ている。部署フィルタを切り替えると、**選ばれたまま画面から消えた人にコマンドが当たる**。
しかも選択行が見えないのでチェックを外せず、「解除」ボタン以外に脱出口がない。

全員に打ちたいときは明示的に全選択させる。

## いま出来ないこと（前提になる工事）

**ドラッグが複数を運べない。**

```ts
// bublys-libs/bubbles-ui/src/lib/utils/drag-types.ts
DragPayload = { type, url, label?, objectId?, sourceBubbleId? }
```

配列も、複数 objectId も、個数のフィールドもない。さらに `dragover` の最中は中身が読めない仕様なので、
**受け入れ側はドロップされるまで「何個来るか」を知れない**。

この穴は選択とは無関係にすでに開いている。

- ポケットの出口は「1件ずつバブルとして開く」だけ。まとめて渡す先がない
- object-transformer の一括変換は、複数オブジェクトを受け取る関数が `return []` のまま止まっている
  （`feature/BatchConvertFeature.tsx:20-23`）

**格上げ（掴んだら選択ぜんぶが荷物になる）はこの器の上に乗るので、ここが先。**

## 実装のときに気をつけること

- **スコープごとに持てば再レンダリングもスコープ内で閉じる。** 学会シフトの配置表は `ObjectView` が
  208個並ぶ（実測）。グローバルな選択1つより、スコープ単位のほうが素直
- 泡の膜は CSS の `:hover` だけで状態ゼロにしたが、**選択は状態なので同じ手は使えない**。
  選択集合を持って `data-selected` を書き、見た目は CSS に任せる形にする
- 選択はバブル単位になる（Finder の選択がウィンドウごとなのと同じ）。いまの hotel も
  コンポーネント単位なので一致する
- Shift / Cmd クリックを一般ユーザーに求めるのは厳しい。チェックボックスの併置は残してよい
  （Finder には無いが Gmail にはある）
