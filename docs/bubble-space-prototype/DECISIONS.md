## 2026-09-19

### 触ると、泡ではなく視点が動く ★ 規則②が変わった

> 「触った泡は手前へ、は多分、微妙だと思う。どちらかというと、**触った泡の方にカメラが寄っていく**感じがいいと思う」

**値を1つも書かなくなった。** これで消えたもの:

- `raise`（触ったとき Z に書く動詞）
- 泡の `order` を X と Z で取り合う問題 ── **「横に並べる」と「触ると主役が変わる」が同時に成り立つ**
- ⑤ との緊張（値を書かないので、触っていない泡は定義上動かない）

実測：coverflow で焦点 X を送ると倍率が `0.31 … 0.98 … 0.31` → `0.03 … 0.98` に変わり、
**泡の値（順序・自由X）は1つも変わらない**。

### 端での下限 ── ★ 入れたが、翌日に取り消した

> 「（右端が隠れてもいいと言ったのは）**あるバブルAの右端が、より手前のバブルBの左側によって隠されても**、
> 後に開いた B にある程度関心事がうつっているのだから、A が多少隠れても構わない場合もあるだろう、ということ」

**「覆われる」と「潰れる」は別物だった。** ここまでは合っている。

★ **ただし「潰れて読めないのは駄目」は masa さんの言葉ではなく、僕（Claude）の解釈だった。**
masa さんが言ったのは「覆われるのは構わない」までで、「潰れるのは駄目」とは言っていない。
翌日そこを正された:

> 「別に**奥に行ったバブルは読めなくてもいい**よ。**雰囲気だけでも残ってることに意味がある**。
> だからこれは全然 OK。ある程度小さくなったバブルは**描画さえしなくていい**し」

**だから下限は要らない。** 入れたことで起きていた不都合も、これで消える:

| 下限を入れて起きたこと | 取り消すと |
|---|---|
| 触った泡が中央まで来ない（焦点が 204 まで届かず 67.1 で止まる） | **届く**（実測 204.0・倍率 0.98） |
| `pack` × 魚眼 が重なるようになった（食い込み −8.3〜−16.6px。隙間による） | **重ならなくなる**（像の幅で描くので） |
| テストの期待値がずれた | 元に戻る |

**代わりに入れるのは「描画の下限」。** 小さくなりすぎた泡は**描かない**（規則ではなく ui の話。
既にある「題名は 6.5px を切ったら描かない」の延長）。

下限そのものは v3 にはあった（`v3/05-kinmuhyo.html` の `SIZE_FLOOR = 0.32`）。
あれは**本物の世界線ビューの数字**で、丸いノードに題名を出さないから足りていた。
題名を出す泡では `12 × 0.32 = 3.84px` で読めない ── **そもそも「読める下限」ではなかった。**

### 新しい泡は、opener の兄弟

`openingPosition` は**3役を兼ねていた**（どこに置くか／開いてよいか／膜を出すか）。分ける:

| いま | これから |
|---|---|
| どこに置くか | **親の View が決める**（①④）。props から消える |
| 開いてよいか | `url` が解けるかどうか |
| 膜を出すか | **掴めるかどうか**だけで決まる |

ダブルクリックとドロップは**もともと同じ道**だった（`openBubble` の第3引数が違うだけ）。
コミット `1f3987b7` に「ダブルクリックが『開いて』なら、ドロップは『ここに開いて』」と書いてある。

### ポップアップは、世界線の打ち消しスナップで戻る

> 「ポップアップは、すぐに元のページにもどっていく前提。あと、比較的小さい。
> だから、**親は下がるには下がって、ポップアップバブルが手前に出る。閉じたら、また親は元の位置に上がる**」

`world-line-graph` に既にある規則を使う:

```js
// 打ち消しスナップ：見込み状態が祖先（＝戻る）／既存の子（＝進む）と一致するなら、
// 新ノードを作らず apex をそのノードへ移す
const snapTarget = this.findSnapTarget(apex.id, prospectHash);
if (snapTarget !== null) return this.moveTo(snapTarget);
```

**カメラは、ハッシュに入れず、ノードに紐づける。**

- 状態に入れると：閉じても**カメラが動いたまま**なのでハッシュが一致せず、戻らない
- ノードに紐づけると：泡の状態が一致 → 古いノードへスナップ → **そのノードのカメラを当てる** → 視点も戻る

カメラは「その世界が**どうだったか**」ではなく「その世界を**どこから見ていたか**」なので、同一性には入らない。

これで **「焦点を世界線に載せるか」の2択に third があった**ことになる ── 載せる／載せない ではなく、
**同一性には載せず、ノードには載せる**。

あわせて、`intent` の仕組みで「16歩ぶんドラッグするとノードが16個」も起きない:

> 世界線のノードは**ユーザーが手を下した1回につき1つ**。意図は pointerdown で開き、次の入力まで閉じない。
> 開いている間に配置が何回変わってもノードは増えず、2回目以降は同じノードを書き換える（amend）。

`intentLabel` の例に既に `open:… / close:…` がある。

### 泡の中身と、子の泡は、別物にする

- **勤務表のセルは泡にしない**（全部泡にすると重すぎる）。ただし **ObjectView ではあってよい**
- そのために **`<table>` ではなく CSS grid** で組む（`<tr>` は table fixup で ObjectView に包めない。実害が出ている）
- **ObjectView は `bubble-layout`（domain）に入らない。** 入るのは動詞だけ ──「この空間の、この点に、新しい泡を置く」
  ObjectView はそれを呼ぶ人の1人（ほかに宇宙のドロップゾーン、ツールバー、ポケット）
- 泡の中身は `renderBubble(id) => ReactNode` で外から渡す。**子の泡は domain の木だけが知っている**
  （`<Bubble><Bubble/></Bubble>` と書けるようにすると、木が React と domain の2箇所にできて剥がせなくなる）

### 補間は CSS transition

> 「いったん CSS transition でいいんじゃない？やってみて重かったりしたら考える。
> （たとえば、中身の描画を完全にやめて泡の枠だけ動かして、移動が終わったら中身を描画しなおす、とか）」

毎フレーム書くのが `transform` 1行だけなので、transition は1行で載る。
掴んでいる泡だけ transition を切る（指から遅れるため）。

重くなったときの逃げ道は実測済み ── 画像に焼く手は、既存 `bubbles-ui`（4段グラデ＋影4枚＋`backdrop-filter`）で
**2.2倍**（54→118fps）。いまの泡は中身が軽すぎて焼き代のほうが高い。

### 焦点より手前は、消す。消えたものは縁に積む ★ 未決が1つ減った

> 「消して。で、自分より手前にバブルがある場合には、**右端に「手前の泡スタック」みたいなものがあって
> スタックにアイコンが積まれる**形にしたらどうだろうか？」

「消える」が怖かったのは、消えたものが**どこにも無くなる**からだった。**縁に積めば怖くない。**

- **止める**は採らない ── 奥の面へ行けなくなる（実測：奥へ4回まわしても焦点 0）
- **薄くするだけ**も採らない ── 越えた面が倍率 20（640×520px）の板になって画面を覆う（実測）

#### ★ ポケットとは別物（ここを一度取り違えた）

> 「ポケットは、**オブジェクトのクリップボード**のようなもの。
> 今僕が言ったのは、**view の要素が視界の外に出た（とりわけ Z 軸的に）場合に、そこに戻れるように積む**というもの。
> **積むという点しか似ていない**と思う」

| | ポケット | 手前の泡スタック |
|---|---|---|
| 何の話か | **中身**（オブジェクト） | **見え**（view） |
| どうやって入るか | **置く**（クリップボード） | **置かない。** カメラがそこにいるから出ている |
| 状態を持つか | **持つ**（置いたら残る） | **持たない。** カメラを戻せば勝手に空になる |

**状態を持たないことは実測済み**（`_carryover/outofview.mjs`）:

```
はじめ        手前へ抜けた 0
ホイール1回    手前へ抜けた 1
ホイール3回    手前へ抜けた 2   ← g2 g3
戻した        手前へ抜けた 0   ★ 勝手に空になった
```

**だから「積む／降ろす」という操作も要らない。スタックは、カメラの位置の関数。**

#### 誰が知っているか

`resolveWorld` は既に `alpha` と `vis` を返している（`placements()` の鍵は
`id x y w h scale local depth space alpha vis implicit`）。**「手前へ抜けた」＝ `alpha === 0` で取れる。**

つまり **domain はもう知っている。ui が決めるのは「どこに、どう描くか」だけ。**
（規則は増えない。新しい状態も増えない）

#### 決めた

- **積まれるのは、その空間の中だけ**（入れ子の奥までは拾わない）
- **アイコンを押すと、カメラが戻る**（触ると視点が寄る、と同じ枝）

> 「いずれは、**空間をぐにゃーんって曲げて、戻る前と戻った後を同じ画面にいさせたく**なることもあるかもしれないけど」

★ これは**規則に置き場所がある**。魚眼はまさに「遠いものを潰して画面に残す」ための曲げで、
いまは X/Y にしか無い（Z は `perspective` と `flat` だけ）。**Z にもう1つレンズを足す**のが自然な置き場所。
いまはやらない。

#### 同じ形の問題がもう1つある

「画面の外へ出て掴めない」（持ち越し中）も、**「視界の外に出たものが行方不明になる」という同じ形**。
`placements()` の矩形と窓を比べるだけで取れるので、同じ仕掛けで拾える可能性がある。
ただし**今回の実測では画面の外へ出た泡は 0 個**だったので、そちらは未検証。

### 描く下限 ── ★ 5.0px に決まった

> 「ある程度小さくなったバブルは**描画さえしなくていい**し」

**規則ではなく ui の話。** domain（`bubble-layout`）には入れていない。`resolveWorld` は今までどおり
`placements` を返すだけで、下限を 0→3→5→10→16→20px と動かしても **`placements` は1バイトも変わらない**（実測）。

**測るものは「倍率」ではなく「画面の px」**（短辺 `min(w, h)`）。既にある「題名は 6.5px を切ったら描かない」
（`MARK_MIN`）と同じ物差しにそろえた。

**5.0px の根拠**（実測）。枠は倍率によらず画面で 1.10px（`--rw` × `--k` で相殺される）。
短辺 5.0px なら `1.1 + 2.8 + 1.1` で、**中身の面が枠2本より広い**。ここを切ると泡は
「色のついた面」ではなく「線の切れはし」になる。7〜8倍に拡大して目でも見た ──
2.9px は輪郭だけの染み、5.9px は色の面として在る、7.4px は角丸の小箱。

★ **低い側に置いた決め手は「消しすぎ」のほう。** カレンダーを 列·等間隔·魚眼 で潰した場面で、日14個が残る数：

```
0px 14/14    5px 14/14    10px 10/14    16px 0/14    20px 0/14
```

16px だと**入れ物（緑の箱）だけ残って中身が空になる** ── まさに「雰囲気ごと消える」。
上げるのはつまみでいつでもできるので、低い側に置いた。

> 「**下限の数は後で適当に決められるでしょ。5px で OK**」

つまみ（`__lab.setDrawMin` ／ ツールバーの range 0〜20px）は**残す**。いつでも動かせる。

`__lab.setDrawMin(px)`／ツールバーの range（0〜20px・0.5 刻み。0 で「なし」）。覚えさせていないので開き直すと 5.0px に戻る。

### 描かなかった泡をスタックに積むか ── ★ 積まない、に決まった

> 「**描かなかった泡も積まないで OK**」

**A（積まない）。** 切り替えは残してある（`__lab.setStackTiny` ／ ボタン「小さいのも積む」）が、既定が答え。
**「積まれるのはその空間の中だけ」も、これで触らずに済む**（下の 1 が要らなくなった）。
札は点線（小さすぎ）と実線（手前へ抜けた）で分かれ、見出しも「手前 N ／ 小 M」と割れる。

選ぶときに効きそうなこと（どれも実測）:

1. **B にしても、たいてい札は出てこない。** スタックは「積まれるのは、その空間の中だけ」という決まり。
   ところが小さく潰れた泡は入れ子の奥にいることが多く、**選択が外にあると B でも 0**。
   同じ画面・同じ2個が消えているのに、選択を写真からメモへ移しただけで札が消える。
   **B を採るなら「その空間の中だけ」も一緒に決め直すことになる。**
2. **A と B は、消えた理由が逆向き。** 手前へ抜けた＝**カメラを戻せば**必ず戻る。小さすぎ＝**カメラを寄せれば**戻る。
   押したときの動き（`focusOn`）は同じなので混ぜても壊れないが、意味は逆。
3. **気づく口はもう1つある。** ツールバーの読みが常に「5.0px　描かない 2」と全空間ぶんの数を出す。
   札が 0 のときもこの数は 2 のまま。**減ったことに気づけるのは、いまのところこれだけ。**

## 2026-09-23 〜 24

### ③ 見えない親に「像を持たせない」── ★ 入れてみて、翌日に取り消した

**入れた理由。** 並びに入った泡は、触っても原寸に戻らなかった
（実測：詳細2つが横に並んだ状態で魚眼 X を掛けると **どちらも 0.58**、どちらを触っても 0.58 のまま）。
並びを1つの体として写しているので中の泡は倍率を共有し、② が動かすのは並び自身の焦点
──並びの箱は中身ぴったりなので約束（`fitFocus`）が 0 へ戻す、という筋。

そこで「並びは**ずれを足すだけ**。中の泡は窓のレンズ・窓の焦点で直に写す」に変えてみた。
狙いどおり、並びの中でも**触った泡が原寸・隣が縮む**ようになった
（札 280×88 を3枚、560px の窓で魚眼 X：`0.443 / 0.924 / 0.443` → 左を触ると `0.924 / 0.443 / 0.081`）。

**取り消した理由 ── 規則の言葉と食い違っていた。**

> 「見えない壁で区切られた状態の中に同一ドメインが新規作成される場合は
> **絶対に魚眼加工前に同じ大きさで配置されるべき**。
> **見えない壁の中のオブジェクトは全部合わせて1つのウィンドウとして扱う。これは絶対揺るがない。**」

並びが「1つのウィンドウ」なら、**中の泡がばらばらの大きさに写ることはありえない**。
魚眼は「並び」という単位に掛かる ── 並べるのは素の大きさで、そのあと**まとめて**レンズを通す。

実測（囲碁 600×570 を2つ、窓 1466×974、魚眼 X）:

| | 囲碁1 | 囲碁2 |
|---|---|---|
| 像を持たせない（入れてみた側） | 0.555 | 0.948 ← **揃わない** |
| 並びを1つの体として写す（いま） | 0.824 | 0.824 |

**残っている宿題。** 取り消したので、入れた理由のほうは**戻ってきた** ──
並びの中の泡は、触っても1枚だけ大きくはならない。
「1つのウィンドウ」である以上それが筋なので、読みたい1枚は**並びから剥がす**か、
**そもそも魚眼を点けない**（下）で対処することになる。

### ★ 画面は2枚ある ── スクロールとズームを分けた

> 「**画面の中に画面を持っているイメージ**って伝わるか？
> 魚眼は決められた画面の中でここはどれくらい見たいな情報を画面に持たせている。これを**画面1**とする。
> その画面1をそっくりそのまま平面の画面として見ているものを**画面2**とする。
> **画面1の仕組みではズームできない状態では画面2の仕組みでズームしろ**って言っているの。」

| | 何か | 何ができるか |
|---|---|---|
| **画面1** | レンズ（① 位置 → 画面）。箱の半幅 `H` は動かない ＝「決められた画面」 | その中で「どこをどれくらい見たいか」（焦点・魚眼） |
| **画面2** | 画面1の像を、そっくりそのまま1枚の平面として見るところ（`compose`） | **寄り引き。上限は無い** |

#### 手の割り当て

| 手 | 動くもの | 止まるところ |
|---|---|---|
| 背景をドラッグ | 海の平行移動（X・Y の焦点） | 約束(1)(2) |
| ホイール | **海の奥行き**（Z の焦点 ＝ 画面1） | 泡のいる範囲 |
| ピンチ（⌘/Ctrl ＋ ホイール）／**左ボタンを押しながらホイール** | **画面2の寄り** | **無い** |

★ **開く動作が拡大。** ピンチを開く（＝ `deltaY` が負）と大きくなる ── どこでもそうなっているので、
ここだけ逆にしない。左ボタンを押しながら、でも寄れるようにしてある（ピンチの無いマウスのため）。
そのとき**掴みかけは捨てる** ── 押していたのは寄るための合図で、動かすつもりではないから。
残すと、寄ったあとの1回目の move で掴んだ点の u が食い違って画面が飛ぶ。

> 「元々のhtmlではマウス操作のスクロールだけは割り当てられてて、ズームは割り当てられてなかったんだよね？」

そのとおり（lab.html 1638-1646 行。ホイールは Z の焦点だけで、Z が なし なら何もしない）。

★ **一度ホイールに2段目を足して、取り消した。** 「奥行きで動けなかったぶんは寄りへ」と
つないでみたが、**奥行きを繰ろうとしただけで画面ごと寄ってしまう**。
画面1でできないことを画面2で肩代わりするのは正しいが、**同じ手に重ねてはいけない**。

#### 寄りは「泡の値」ではない

焦点と同じ**視点の値**（`world.zoom`）。触っても書かれず、ホイールでも書かれず、ピンチだけが書く。

**寄りを持つのは画面2だけ。** 窓（空間を持つ泡）の中は画面1 ── レンズが「位置 → 箱の中の像」を
決めるところで、箱の大きさはその窓のもの。そこに寄りを足すと**中身が窓の外へ溢れる**
（一度そう作って踏んだ：一覧の札が 280 → 2241px になり、420px の窓を突き抜けて海じゅうに散った）。
窓の中でピンチしても、動くのは画面2の寄り ── **窓ごと大きくなる**ので中身も一緒に大きく写る。
（実測：窓 420 → 1334px、中の札 280 → 889px。どちらも同じ 3.18 倍で、札は窓の中に居たまま）

**画面2は1枚しか無い。** 入れ子の海（窓の中・岸に貼った一覧）は画面1 が深くなっただけで、
平面はいちばん外のひとつきり。海ごとに寄りを持たせると**掛け算になる**
── 入れ子の海は DOM も入れ子なので、ホイールが内側と外側の両方の海に届き、
**それぞれが 2 倍になって 4 倍に写った**（実測で踏んだ）。直したのは2つ:

- ホイールを食うのは**いちばん内側の海ひとつだけ**（`stopPropagation`）
- 寄りは自分の世界に書かず、**外の画面へ渡す**（`ScreenZoomContext`）。
  外に画面が無ければ自分がいちばん外 ＝ 自分の世界が持つ

実測（自由に置く・泡 420×520 を5枚・窓 1466×974）:

```
ホイール  −1 段で 0.794、そこで止まる（泡が全部 z 0 なので焦点は [−1, 0]）
ピンチ    開く 1.260 1.588 2.000 2.520 3.176 4.002 5.042 6.353 …
          閉じる 0.794 0.630 0.500 0.397 0.315 0.250 0.198 0.157 …
```

行って戻れば寄りはぴったり 1 に戻る。1 刻みの比はホイールもピンチも `1 + K_PERSP` ＝ 1.26 で
そろえてある（奥行きを 1 段繰るのと寄りを 1 段動かすのとで、手の感じが変わらない）。

★ ピンチは**ネイティブの listener で受ける**（`{ passive: false }`）。React の `onWheel` は
passive なので `preventDefault` が効かず、ブラウザの拡大に取られる。ラボも同じにしている。

### 岸に地を敷いた ── 岸は画面2に合成された層

> 「画面2のズームの際、**岸は画面2に合成されていると思って。端に維持して**」
> 「岸に地を敷いて」

**端に維持する**ほうは、もともとそうなっていた（実測：泡を 1.0 → 4.0 → 5.0 と寄せても、
岸の矩形は `0,0 60x832 | 54,0 480x44 | 723,784 48x48` で 1px も動かない。
岸は `anchoredRect(dock, size, viewport)` で窓の縁に貼られていて、寄りを引数に取らない）。

**足りなかったのは地のほう。** 岸の入れ物は地を持っておらず（`background: rgba(0,0,0,0)`）、
`ground: "none"` の泡は**海がそのまま透けていた**。後ろがいつも暗い海だったので成り立っていたが、
寄れるようになると白い泡が岸の下を通り、見え方の帯の字が飛ぶ（実測：5 倍で読めない）。

岸が画面2に合成された層なら、**下を何が通っても岸は岸として読める**はず。
岸の札 1 枚ずつに、海と同じ地（`SEA_GROUND`）を敷いた ──
色は海と同じものなので、**敷いても見た目は1ピクセルも変わらない**。
変わるのは「後ろに何が来ても変わらない」ということだけ。

★ **地は管（ネオン）と同じ形に切り抜く。** 敷くまでは角に何も無かったので要らなかったが、
敷いた途端、**四角い地の角が管の丸みの外へはみ出して門のように角が立つ**。
丸めるのは**両隣の辺に管が走っている角**だけ ── 接している辺には管が走らず、そこは
画面の縁まで地がまっすぐ続くので角は立てたまま（`shoreCornerRadius`）。
実測：見え方の帯は下の2つだけ 14px、ポケットは左上だけ 14px、ランチャーは全部 0。


### 一覧の札は、箱の中身いっぱいに

一覧の中の余白を測ったら、**左右 70px・上下 66px** に対して**札どうしの隙間は 4px** だった。
札（280）が箱（420）よりずっと細いので、中身が箱の真ん中に小さく浮いている。

広く取ってあったのは「右の余白に口（＋新規）を収める」ためだったが、
口の幅（60 ＋ 隙間 8）に対して余白は 56 しかなく**そもそも収まっていない**
── 口は上の帯へ回っていた（`pickPreset` の `needsBand`）。**誰の役にも立っていない余白**だった。

札の幅を箱の中身いっぱい（`LIST_BOX.width − PAD×2` ＝ 392）にした。左右に残るのは枠の余白だけ:

```
前  左右 70 / 70   札 280
後  左右 14 / 14   札 392
```

★ **透視（奥行きに重ねる）では、札は細いままにする。** 子の空間の消失点は
「自分の中身の箱の左上の角」なので、奥へ行った札の左端は `cx + vp.x·(1−m) − (幅/2)·m`。
**幅がちょうど中身の箱いっぱいだと `幅/2 = |vp.x|` で `m` の項が消え、奥も手前も左端が揃う**
（実測：どの札も 84.0）。揃うと手前の札が後ろをまっすぐ覆ってしまうので、
透視のときだけ札を左右 56px ずつ細くして階段に戻す（`LIST_DEPTH_INSET`。実測：左端 90.6 → 140.0）。

**札の幅は並べ方で変わる。** 書くのは顔ぶれ・並べ方と**同じ1回**（`setChildren`）。
一度「札の大きさは札のもの」で通そうとしたが、詰める一覧で余白を消すことと、
透視で後ろの肩を出すことは**同じ幅では両立しない**（どちらも消失点との関係で決まる）。

あわせて `pickPreset` の要り高の見積もりを直した ── 隙間を既定の `GAP`（14）で測っていたが、
実際の一覧の隙間は `LIST_GAP`（4）。高く見積もって**早く奥行きへ切り替わって**いた。

### 札と札のあいだを、限界まで細く

見えている隙間は「**並びの隙間 ＋ 札の上下の余白 × 2**」。前は 4 ＋ 7×2 ＝ **18px** あった
── 札どうしが離れて、一覧というより「札の集まり」に見えていた。

- 並びの隙間（`LIST_GAP`）4 → **0**
- 縦に詰める一覧では、札の上下の余白 7 → **1**（`space-css` の `.bl-packed`）

白い箱どうしのあいだは **2px**（実測）。左右はそのまま ── 詰めたいのは札どうしのあいだで、
枠との余白ではない。

★ **泡になったら、下にも左右と同じだけ余白を置く。** 上下 1px は「札どうしを細く」のためのもので、
選んで装いが出たら話が別 ── 枠と中身が下だけぴたりと接して、左右 7px と揃わない。
泡になった札は 上 27（装いのぶん）／**下 7（左右と同じ）**。伸びる高さは
`(27+7) − (1+1) = 32` ── **中身の高さは変わらず**（実測：118px のまま）、
その 32px ぶん**並びの後ろの札がずれる**。

★ **透視（奥行きに重ねる）には掛けない。** `.bl-packed` が付くのは詰める並びのときだけで、
そちらの札は `top: 7px / bottom: 7px` のまま（実測）。重なって見える並びで余白を削ると、
後ろの札を余計に覆ってしまう。並びの隙間のほうも、X・Y が「なし・そのまま」なので
どう変えても位置は1px も動かない。

### 端は 1 つ。越えようとしたら**跳ね返す**

> 「今は一番先頭を表示しようとZのズームアウトをすると**二番目の位置に先頭が来る**ように
> 設定してあるが、これを一旦1番目で止めるようにしよう」
> 「無理そうなので、googleがよく採用してるこれ以上いけないよっていう**バウンスアニメーション**にします」
> 「バウンスも**1回**で良い」

手前の端は**先頭の泡の面**（`min(ps)`）。ラボは 1 段向こうまで退いていたが、それだと
先頭を出そうとすると**先頭が 2 番目の位置に来て**しまう。

★ 「1 回目は先頭の面、もう一度やってその向こう」も試したが、ホイールは一続きで何十回も来るので
**素通り**してしまい、手の続き具合（何 ms 空いたか）を見るしかなくなって具合が悪かった。**取り消した。**

**代わりに跳ね返す。** 端で回し続けたとき、**焦点をそのフレームだけ端の向こうへ出して戻す**
（`resolveWorld` の `nudge`。山は `sin` で **1 つだけ**・260ms）。**世界には1ミリも書かない**。

- 行き過ぎる量は**軸の 1 刻みの 0.2 倍**。`METRICS.Z_FRONT_KEEP`（0.35）より小さくしないと、
  行き過ぎた瞬間に手前の札がレンズに消される
- 跳ねるのは**面が 2 つ以上ある透視の並び**だけ。Z に次元が無い空間（縦に並べる など）や
  面が 1 つしかない海で跳ねると、「効かない」を「端だ」と言い違えることになる
- 跳ねるのは**その空間の中身**。はじめ層ごと（`.bl-layer`）に当てていて、
  **一覧を載せている窓ごと**跳ねてしまった ── 端にぶつかったのは一覧であって窓ではない

★ **ホイールの受け手は `wheelSpace()` に切り出した。** 札の上で回すと、カーソルの下は「札」なので、
そのままでは `layout.spaces` に無い id になる。`wheelZ` は中で外へ通していたが、
呼ぶ側（ui）が別に出していたので**札の id のまま判定して**いた ── 跳ね返りが出ず、
しかも「動いたか」も札の id で比べていて**ホイールそのものが効かなくなって**いた（実測で踏んだ）。
出し方は 1 つにする。

### （取り消し）手前へは 2 段で止まる ── まず先頭の面、もう一度やってその向こう

> 「今は一番先頭を表示しようとZのズームアウトをすると**二番目の位置に先頭が来る**ように
> 設定してあるが、これを一旦1番目で止めるようにしよう。
> 勢いよくズームアウトすると1番目の位置で止まる。さらにやろうとすると、2番目の位置で止まる。」

焦点の約束（1）「見ている所には泡がある」の手前の端を、`min(ps) − 1` の一息から**2 段**にした。

- 1 回目 ── **先頭の泡の面**（`min(ps)`）で止まる。先頭を見たいだけなら、そこが行き先
- すでにその面にいて、もう一度やったら ── そこからさらに 1 段だけ退ける（全体を見る）

前は一息に 1 段向こうまで退いていたので、先頭を出そうとすると**先頭が 2 番目の位置に来て**いた。

★ **止まるのは「手が続いているあいだ」。** ホイールは一続きで何十回も来るので、
「次の 1 回で向こうへ」だけだと**素通り**してしまう（実測：勢いよく回すと先頭で止まらない）。
入力の側で一続きの手（前のホイールから 250ms 以内）かを見て、そのあいだは先頭の面で止める。
**ただし、いま居る所より手前へは引き戻さない** ── すでに向こうに居るなら、そこが下限
（これが無いと、向こうまで退いたあと回し続けたときに先頭の面へ戻ってしまう）。

実測（ユーザー一覧 30 人。先頭の札の倍率）:

```
奥へ 5 段                      20.000
勢いよく一続きに 15 回          1.000   ← 先頭の面で止まる
手を離してまた一続きに 10 回    0.794   ← その向こうへ 1 段だけ
さらにもう一度                 0.794   ← そこで止まる
```

### 一覧の口と1枚目のあいだが間延びする ── 並びは「空けた量のすぐ下」から積む

④ 詰める並びは箱の中央に来るので、札が少ないと**余りが上にも回って**口と1枚目が離れる
（実測：囲碁 3 件で 150px）。`View` の軸に「**始端に空けておく量**」（`reserve`）を足して、
並びごと動かし、空けた量のすぐ下から積むようにした（実測：天から1枚目 90 → 55.6、余りは全部下）。

★ 動かす量は**箱と中身から毎フレーム決める**（`resolve.ts`）。固定の数で持つと、札が増えたり
選んで背が伸びたりしたときに狂う ── 中央ぞろえの余りは中身の高さで変わるので。
★ 箱は動かさない（`measure` は触らない）。入らないときは何もしない ── そこは並べ方の切り替えの仕事。

### 透視は**必ず**階段にする／口の取り分は 1 回だけ

**階段。** 子の空間の消失点は「中身の箱の左上の角」なので、札の幅が中身の箱いっぱいだと
`幅/2 = |vp.x|` で奥行きの項が消え、**奥も手前も左端が揃う** ── 後ろの札が**上からしか覗かない**。
左からも覗くように、透視のときだけ札を左右 56px ずつ細くする。
幅は**箱から測る**ので、箱の大きさを変えても必ず階段になる（実測：左端 90.6 → 96.1 → 140.0）。

**口の取り分。** ④ 詰める並びは箱の中央に来るので、上に口の場所を空けるには
**上下に同じだけ**余らせるしかなく、口の高さの 2 倍を取られていた。
`View` の軸に「**始端に空けておく量**」（`reserve`）を足して、並びはそのすぐ下から積む ── 取り分は 1 回で済む。

```
前  取り分 = 口の高さ × 2   札 4 枚で奥行きへ落ちる（最後の札と縁のあいだに余白が残っているのに）
後  取り分 = 口の底 − PAD                  札 5 枚まで縦に並ぶ
```

口そのものも 1.5 倍（48×26 → 73×39）にして、**右の余白を札とそろえた**（枠から 14px。
中身の箱はもう 7px 内側にいるので、口は中身の箱から 7px）。
口の下には 10px の隙間を空ける ── そのぶん一覧の箱を 520 → 540 にして、入る枚数を変えないようにした。

**上下の余白はまだ 66px ある。** ④「詰める並び」は**箱の中央**に来るので、中身が箱より低いぶんが
上下に割れる。これを詰めるには「並びを上から積む」という揃えが要るが、それは
横に並べる・くっつきの並びにも効く話なので、規則として決めてからにする。**未決。**


### 窓の枠も岸にする ── 岸を「器」に切り出した

> 「今、ネオンとして開かれるバブリに岸の機能を反映します」

窓（空間を持つ泡）の枠は**ネオンを 1 本描くだけ**で、貼る機能が無かった
── 貼れる先がいちばん外の海にしかなかった。岸の一式（貼り付き・横取り・予告・剥がし・
管の網・地・角の丸み）を `ShoreSpace` という器に切り出して、外の海と窓の両方で使う。

`ShowreLayer` も `anchoredRect` も最初から `viewport` を引数で受けていたので、
**入れ物を選ばない作り**にはなっていた。足りなかったのは「岸を持つ器」が外の海専用だったことだけ。

- 窓の岸に貼れるのは、**その窓の中の海から出たもの**だけ（中と外は別の世界。またぐ仕掛けは持たない）
- 岸に貼った泡から開いたものは、**その岸が載っている海**に出る
- 定位置（ランチャー・見え方・ポケット）は**外の岸だけ**のもの。窓の岸は空で始まる
- 地は器の引数（外は `SEA_GROUND`、窓は自分の夜空 `WINDOW_GROUND`）

★ **踏んだこと2つ。**

1. **止まらなくなった。** 窓は `viewport={{ w, h }}` をその場で作って渡すので、
   器が中に置いた口の見張りが「口が変わった」と拾って描き直し → また新しい object …。
   器の側で**数から作り直して**下へ渡す。
2. **貼った中身が空になった。** 窓の岸に貼ったものは、窓自身の `CurrentBubbleContext` を
   引き継いでしまう（窓は外の海の泡として描かれている中に居るので）。一覧は
   「自分は海の中の泡だ」と判断して、岸用の小さな海を作らずに終わる。
   器の側で**「いまどの泡の中か」を切る**（岸に貼った泡は、どの泡の中でもない）。


### 岸だけで埋めてよい ── 海が無くなることは許す

窓の中で、左に全高の泡を貼ったあと**反対の右の縁に 2 つ目を貼れなかった**。
落とした泡は貼られずに海へ戻る（＝「海に飲み込まれる」）。

原因は規則ではなく**順番**だった。`fitAmongDocked` は「貼っていない向きから先に収める」と
決め打ちしていて、まだ横に縮んでいない矩形は先客と横で重なっているので、
縦を先に見ると「空きゼロ」と出て `null` になる。横を先に縮めれば 370 幅で入る。

どちらを先に見るかは決め打ちできない ── 上に全幅の先客がいれば縦から、
左に全高の先客がいれば横から縮まないと入らない。なので
**滑る向きを先に見て、駄目ならもう一度、貼った向きを先に見る**。

あわせて、**海の取り分は残さない**と決めた。縮み先は先客の縁までで、
岸だけで画面が埋まってよい ── 昔ながらの分割レイアウトとして使う人がいる。

### 海の位置は動かさない。動かすのは「開いたものの行き先」だけ

「岸で狭まったときに魚眼の中心を開いている口へ寄せる」を入れて、**取り消した**。
海は `left`/`top` の平行移動で動くので、中心を寄せると中身が丸ごと同じだけずれる。
窓（幅 560）を左に貼ると海が 280 右へ動き、右側にいた泡が画面の外へ出た（実測：@−221）。
狭くなったのは**見えている所**なので、海を動かして合わせにいくと見えていた所まで連れて行く。
やるならレンズの箱（`H`）の中心を動かす口が要る。箱ごと口に縮めるのも駄目で、
海が 151 しか残らず魚眼が中身を潰した（実測：倍率 6e-05）。

**代わりに、動かす先だけを変えた。** 岸は海の上に重なって描かれるので、窓の真ん中が
岸の下に入っていることがある。そこへ開くと泡の半分が岸の地に隠れる（実測：窓の左半分を
一覧が占めた状態で詳細を開くと、枠ごと左が切れて「Admins」が「nins」になった）。
岸の食い込みから**開いている口**の矩形を出し、`BubbleSpace` の `openArea` →
`bringToCenter` の「真ん中と見なす点」に渡す。

- 海は 1mm も動かない ── ⑤（触っていない泡は画面の上で動かない）を守る
- 変わるのは**開いたものがどこへ来るか**だけ
- 岸が無ければ口＝窓なので、今までとまったく同じ

★ **一度しくじった：止める条件だけ変えても、行き先は変わらない。**
  `bringToCenter` は `screenToAxis(L, axis, now)` を焦点にする ──「いま泡が写っている所」を
  焦点にすると、それが**箱の真ん中**へ来る、という書き方。`want` は「もう合ったか」を
  見るためだけに使われていたので、口の真ん中を渡しても行き先は箱の真ん中のままだった
  （実測：渡す前と絵が変わらなかった）。像を `want − now` だけずらしたいので、
  焦点にするのは **`now` から、ずらしたいぶんだけ戻した所** ＝ `now − (want − 箱の真ん中)`。
  渡さなければ `want ＝ 箱の真ん中` で式が `now` に戻り、今までと 1 文字も変わらない。
- 外の海では口の中心と窓の中心の差は (6, −2) しかない（ランチャー・見え方の帯・ポケット）
  ── 効くのは窓の中で岸が大きく食い込んだときだけ

魚眼の中心（レンズの箱 `H` の中心）を口に合わせるのは、まだ持ち越し。

### 岸の取っ手も、ボタンが離れていたら掴みを捨てる

海のドラッグでは直していた「離しを取りこぼすと、指を離しても付いてくる」が、
**岸の取っ手には入っていなかった**（別の手なので）。窓の中で岸を広げようとすると、
範囲変更のカーソルが掴んだまま離れないことがある。

`onGripMove` の頭で `e.buttons === 0` なら黙って捨て、`lostpointercapture` も拾う。
ただし捕捉が外れただけで**剥がして海へ返すことはしない** ── 離したわけではないので。


### 分け合っている線は、どこを通って来たかで決まる

2 枚が接すると、その線は**両方の中に居る**。掴んだだけではどちらを変えたいのか決まらない
（掴んだ辺＝掴んだ相手、にはならない）。決め方は、岸の `active` と同じ ──
**通ってきた側のもの**を相手にする。

| どこを通って線に来たか | 何が動くか | カーソル |
|---|---|---|
| 線を横切って、**小さい側**から（左・上） | その 1 枚だけ | `ew-resize` / `ns-resize` |
| 線を横切って、**大きい側**から（右・下） | その 1 枚だけ | `ew-resize` / `ns-resize` |
| 線に**沿って**（端の外から回り込む／線をなぞる） | **両方** ＝ 境目が動く | `col-resize` / `row-resize` |

「通ってきた側」は、カーソルの跡のうち**線から離れていた最後の所**で読む。線の上では
どちらの体の中かが決まらないので、位置だけ見ても答えが出ない。

★ **「端の外から回り込む」だけでは足りなかった。** 線の端が画面の縁に着いていると、
外に出られる場所が無い（ランチャーと見え方バーの線は上端が y=0、窓を左右で分けた線は
上下とも縁）。実測でも「下からは効くが上はほぼ反応しない」。そこで、線のそばを
**線に沿って滑って来た**ときも「沿って来た」と読む。測るのは**線のそばの跡だけ**で、
体の中を線と平行に動いてから一歩入る場合は巻き込まない。

★ 跡は画面の座標で取れるが、線は**器の座標**にある。いちばん外の海は器が 0,0 なので
一致してしまい気づきにくいが、**窓の中では全部ずれる**。読む前に器の座標へ直す。

1 枚だけのときは今までどおり、隣の縁で止まる（伸びない／縮むのは自由）。
境目のときは**片方が伸びたぶんだけもう片方が縮む** ── 海は増えも減りもしない。

実測（ランチャー 0..60 と見え方バー 54..534 は管を共有していて、すでに境目）:

```
下の海から近づく       col-resize「境目を動かす（両方が変わる）」
線を上端からなぞる     col-resize   ← 端が縁に着いていても効く
  +70 引く             ランチャー 60→130 ／ バー x 54→124, 幅 480→410
  -70 で元どおり       ランチャー 60     ／ バー 54, 480
ランチャーの体を通る   ew-resize「大きさを変える」
  広げる               変わらない（隣が居る）
  縮める               ランチャー 153→93 ／ バーはそのまま
バーの体を通る         ew-resize（動くのはバーの左辺）
```


### 平行の軸では、触っても寄らない

> **選択できているということは、もう見える範囲にあるということ。**

②「触った泡へ視点が寄る」を X・Y・Z ぜんぶに掛けていたため、平行に詰めた一覧で札を選ぶと
**選んだ札が箱の中央へ来るぶん、並びがまるごとずれて**いた。上に何も無いのに先頭の札が
箱の中央まで下がり、＋新規の口が次の札に隠れる。最後の札を選ぶと逆に並びが上へ寄って
下が空く（どちらも実測）。

平行は倍率が一定なので、寄っても見え方は 1mm も変わらない ── 動くのは中身だけで、
得るものが無い。②の値打ちは「**端で潰れている泡が、中央で原寸に戻る**」ことなので、
そこは魚眼と透視の Z に残し、**平行の軸では何もしない**。

| その空間の軸 | 触ったとき |
|---|---|
| 魚眼の軸 | その泡がその軸の焦点になる（中央で原寸） |
| 透視の Z | その泡の面が焦点になる（奥の札が手前に来る） |
| **平行の軸** | **何も起きない** |
| 送れない軸（次元が なし ／ 箱にぴったり） | 何も起きない |

焦点の約束（`fitFocus`）は変えていない ── 送れば今までどおり箱の余りぶんで止まる。
変えたのは「触ったときに送るかどうか」だけ。`bringToCenter`（**開いた**ときに中央へ）は
別の用事なので、そのまま。


### 海の箱 ── 岸が食い込んだとき、海をどう扱うか（4 回やり直した）

**結論：海は動かさない・大きさも変えない。口が効くのは「開いたものの行き先」だけ。**
（下の 1〜3 は経緯。3 を採ったあと 4 で戻した）

岸が食い込んでいるとき、海をどう扱うかで 3 回やり直した。

1. **海ごと口の中心へ寄せる** … 平行移動なので**中身が丸ごとずれる**（実測：残った一覧が @-221）。取り消し
2. **海は窓いっぱい・開いたものの行き先だけ口の中心** … 新しいものは口に来るが、
   **押しやられた側**が窓の左端まで行って岸の下に潜る（実測：2 つ目で 1 つ目が @747、
   3 つ目で @631。岸は 0..745）。取り消し
3. **海の箱＝口**（採用）… 位置も大きさもレンズの箱（`H`）も口で決まるので、
   「左へずれる」も岸の縁で止まる

実測（窓 1560×1060・岸 0..745・海の箱 815×1060 を器の 745.. に置く）:

```
① 一覧の札から開く      A  943..1363
② A の中から開く        A  773..924 ／ B  959..1346
③ B の中から開く        A  756..823 ／ 並び 841..1472（B 841..1153 ／ C 1153..1473）
```

どれも口（745..1560）の中に収まる。2 でやった `bringToCenter` の「真ん中と見なす点」は、
箱が口になれば同じことなので**外した**（同じことを二重に持たない）。器は口を
**窓として**渡すので、ドメインは岸を知らないままでよい。

★ 海の層は口の左上に置くので、ドラッグの知らせは**海の座標 → 器の座標**に直して岸へ渡す
  （`toShore`）。これを通さないと、右の縁へ持っていっても手前だと思われて貼れない。

**4. 海は窓いっぱいのまま。口は「切り取る窓」としてだけ効かせる**（採用・3 を戻した）

3 を入れたら、**岸のくっつき方を変えるだけで海の中身が動き、大きさまで変わった**。
「タスク管理を岸にどう着けるかで、剥がしたバブルが見えなくなったり見えるようになる」の正体。

```
右の縁に着いている（口 1285）    泡 器で 343..942   倍率 0.923
どの縁にも着いていない（口 1915） 泡 器で 644..1271  倍率 0.963
```

泡は 1 つも触っていないのに 300px 動いて大きさも変わる。岸の地は不透明なので、
動いた先が岸の下だと**消えて見える**。これは 2 つに反していた:

- **⑤ 触っていない泡は画面の上で動かない**
- **「自分で狭めたのなら、残りに小さく全部見せるより、前と同じ大きさで見切れる方がいい」**
  ── 箱（`H`）が縮めば中身も縮む ＝ まさに「小さく全部見せ」に行っていた

なので **海は位置も大きさも変えない**。口が効くのは `bringToCenter` の「真ん中と見なす点」＝
**開いたものの行き先**だけ。岸の下に入ったものは**見切れているだけ**で、海をドラッグすれば
見に行ける ── 2 で「押しやられた側が岸の下に潜る」を不具合として取り消したが、
**原則に照らせばあれは見切れ**だった。

実測（海に泡を 1 つ置いて、ランチャーを 60 → 300 → 60 と広げ戻す）:

```
ランチャー  60x832 → 300x832 → 60x832
海の泡      @140,404 51x23 → @140,404 51x23 → @140,404 51x23   ← 1px も動かない
```

★ 魚眼の歯止め（箱の 2 倍）はそのまま残した。箱が縮まなくなったので出番は減るが、
  規則としては正しい。

### 魚眼は、箱の 2 倍を超える泡は諦める

海の箱を口にすると箱が狭くなり、そのままでは魚眼が中身を潰す。歯止めを対で入れた。

> **自分で狭めたのなら、残りに全部を小さく収めるより、前と同じ大きさで見切れるほうがいい。**
>
> 見切れていると「枠をもっと大きく取ろう」という心理が働く。**無意識の見辛さを、自分で解決する。**
> 何より小さくなりすぎないのでストレスが少ないし、**岸にどれくらい割り当てるかを考えさせられる**
> ── この大きさで見るには、これくらい要る、と。

これが歯止めの「なぜ」。**縮めて収めるのは、狭めたのが自分でないときの親切**であって、
自分で岸を広げた結果まで面倒を見にいくと、狭くしたことの手応えが消える。
だから諦めた軸は平行のまま見切れさせる（掴んで寄せれば見に行ける）。

★ 境目の 2 倍は、この考えの上での**妥協点**でもある。理屈だけなら「自分で狭めたときは
  いっさい縮めない」まで行けるが、それだと開いた直後の並びまで見切れるので、
  「収めればまだ読める」ところまでは収める、で止めてある。

魚眼は「中身を箱に収める」ためのものだが、箱よりずっと大きい泡を収めにいくと、
その 1 つが箱を埋めきって**ほかがぜんぶ潰れる**。収めた結果が読めないなら収めない方がまし
── 諦めた軸は平行になる。はみ出したぶんは器が切るが、掴んで寄せれば見に行ける。

見るのは**いちばん大きい泡 1 つ**と箱の対比だけで、枚数は見ない
── coverflow のように何枚あっても、箱が泡なみに広ければ焦点のまわりは読める。

```
箱 151 に泡 420（2.8 倍）    窓を岸に貼って海が 151 しか残らなかったとき。
                            倍率 6e-05 ＝ 描く下限を切って消えた  → 諦める
箱 815 に並び 840（1.03 倍） 詳細を 2 つ開いて並びになったとき     → 諦めない
```

★ はじめ「泡が原寸で入らなければ諦める」（1 倍）にしたら後者を巻き込み、並びが平行のまま
  岸の下へ散った（実測：A が 248..668）。境目は 1 倍ではなく **2 倍**。

★ ついでに分かったこと：**開くと X が魚眼になる**（`openAt`。`keepLens` が立っていなければ）。
  窓の中の海も、1 つ目を開いた時点から魚眼。「窓の中は平行だから関係ない」は誤り。

### 中身を描く物差しは、海ごとに閉じる

`Placement.scale` は入れ子を掛け合わせた**画面の**倍率（`compose` で `hostScale(host) × local`）。
中身を描くかどうか（`CONTENT_MIN`）をこれで見ていたので、**窓の中の泡が、外の海と同じ
画面の大きさで中身を失って**いた。窓はそれ自体が縮んで写るので、中の泡は自分の海を
いくら占めていても消える。

見るのは**自分の海の中での縮み**（`scale ÷ その空間の倍率`）だけにした。
絶対の下限は**窓が受け持つ** ── 窓が小さくなれば窓ごと中身を描かなくなるので、
中の海はそこで丸ごと消える。物差しが海ごとに閉じて、入れ子でも同じ言葉で通る。

題名（`MARK_MIN`）と描く下限（`DRAW_MIN`）は**絶対のまま**。字は読めなければ出す意味が無い。

実測（外の海も窓の中も魚眼、窓が 0.950 で写る場面）:

```
窓          画面の倍率 0.950   自分の海の中 0.950
窓の中の泡  画面の倍率 0.740   自分の海の中 0.779   ← 窓ぶん(0.950)が割り戻される
外の海の泡  画面の倍率 0.987   自分の海の中 0.987
```


### 辺に役割は無い ── どう引いたかで決まる

岸の取っ手には、**役割が辺に固定されていた**:

> 留まっている辺 ＝ 剥がす／滑る　｜　自由な辺 ＝ 伸縮

これだと**くっついた辺が増えるほど伸縮できる向きが減る**（ゼロサム）。ランチャーは
`left`・`top`・`bottom` の 3 辺が留まっているので**右辺でしか伸縮できず**、高さは変えられなかった。
4 辺くっついたら伸縮する手が 1 つも無くなる。

さらに、「くっついている」が**2 つ別々にあって食い違って**いた:

| | 出どころ | 使う所 |
|---|---|---|
| 留め方 `dock.edges` | 落とした瞬間のカーソル（`edgesNear`） | 取っ手の役割・`anchoredRect` の留め |
| 見た目 `touchingEdges` | いまの矩形と窓 | 管・角丸・地の切り抜き |

留め方は**その後どう形を変えても更新されなかった**ので、伸ばして 2 辺目に届いても辺は増えず、
くっついて見えるのに剥がす動きが無い、という食い違いが出た（「孤立した岸」も、おそらくこの姿）。

**決めたこと。**

1. **くっついているかは、いつでも矩形から読む。** 留め方を覚えるのをやめ、動かすたびに
   `touchingEdges` で引き直す。最初に貼るときも、狙った辺は `fitAmongDocked` の寄せ先として
   渡すだけで、覚えるのは**結果の矩形から引き直した辺**
2. **辺に役割は無い。引いた向きで決まる。** 辺と直交して引けば**その辺が動く**（伸縮）、
   辺に沿って引けば**体ごと動く**（滑る／縁から離せば剥がれる）。決めるのは
   **一続きの手につき 1 回**で、`GRIP` ぶん動くまで決めない
3. **どの縁にも触れなくなったら海へ返る**（カーソルが縁から遠いか、ではなく矩形で見る）
4. **剥がしたら、掴んだときの大きさで返す。** 辺を内へ引いて縁から離すのが剥がす動きなので、
   その途中で縮むのは**手段**であって結果ではない。縮んだまま返すと剥がすたびに泡が痩せる。
   置く所は剥がした所のまま（飛ばない）

これで役割が辺の本数に縛られなくなり、ゼロサムが消えた。実測（窓 826×832）:

```
① ランチャー（3 辺くっつき）の上辺を下へ   60x832 → 60x705    ← 前は高さを変えられなかった
② そのまま上辺を上へ引き戻す                60x705 → 60x832    ← 2 辺目に届いてその場でくっつく
③ 見え方バーの上辺を横に引く                @54 → @234         ← 沿う ＝ 体ごと滑る
④ 見え方バーの上辺を下へ引いて剥がす        海へ @234,8 480x44 ← 縮んだぶんは戻り、位置は剥がした所
```

★ **引き換え**：貼っている辺を掴んでそのままカーソルで別の縁へ運ぶ、が一手では出来なくなった
  （辺を引くのは縮めること）。滑るのは同じ縁の上だけで、運ぶのは「縁から離して海の泡に戻してから、
  ふつうに掴んで運ぶ」の二手。ここは**許容と決めた**。

★ **まだ出来ていない**：**先客の辺を岸として使うこと。** くっつく相手は今も「窓の縁」だけで
  （`edgesNear` が見ているのは窓の縁）、先に貼ったものは `fitAmongDocked` /
  `clampResizeAmongDocked` で「ぶつかる相手」として扱われるだけ。広げるなら
  「外へ引く＝剥がれる」の“外”が窓の外ではなく**隣の体の中**になるので、そこを決め直す必要がある。


### 岸と海では、同じ「大きさ」が違うものを指す

海に浮いている泡には**バブルUI（ヘッダ）が付く**が、岸に貼ったものには付かない（管と中身だけ）。
泡の大きさをそのまま渡していたので、貼った瞬間に中身がヘッダのぶん広がり、
剥がすと逆に**ヘッダに食われて縮んで**いた。

揃えるのは**中身の大きさ**。だから渡すときに飾りのぶんを引き、返すときに足す。

> 「剥がしたら同じ大きさ」は**中の要素**の話で、ヘッダを含んだ泡全体のことではない
> ── バブルUI が付くぶん、泡そのものは大きくなる。

実測（`METRICS.HEADER` ＝ 24）:

```
岸  480x44  →  剥がす  →  海 480x68  →  貼り直す  →  岸 480x44
```

★ まだ合っていないのは**中身の枠の内側**：海の泡の本文は左右 7px の余白を持ち、
  岸の中身は管の厚み（6px）ぶん内側にある。上の往復で本文の枠は 480x44 → 466x34 で、
  この差ぶんは残っている。名前の付いた食い違い（ステータスバー）は消えたが、
  **ぴったり揃えるには本文の余白と管の厚みも引き算に入れる必要がある** ── 保留。


### 管は 1 つの枠に 1 本 ── 消すのは枠 1 本だけ

岸に着いた窓の中で、**岸の管が丸ごと消えて**いた。

犯人は CSS だった:

```css
[data-docked-url] [data-frame-shore] [data-showre-tubes]{display:none}
[data-docked-url] .bl-body [data-frame-shore] [data-showre-tubes]{display:block}
```

言いたかったのは「岸に着いた窓の**枠**は、岸の管が引き受けるので描かない」。けれど
**岸に貼ったものはバブルの装いを持たない**ので `.bl-body` が無く、戻す 2 行目が効かない。
窓の枠だけのつもりが、その窓が持っている**中の岸の管ごと**消えていた
（実測：path は 8 本正しく出ているのに `display:none`）。

CSS では「枠の輪」と「中の岸の輪」を区別できない ── 同じ 1 枚の SVG に入っているので。

なので**器に持たせた**：`ShowreLayer` / `ShoreSpace` の `frame`（既定 true）を false にすると、
**自分の枠の輪だけ**描かない。岸に貼られていることは `OnShoreContext` で中身へ伝わり、
`WindowSpace` が `frame={!onShore}` を渡す。

```
前  窓の管 display=none path=8   ← 枠も中の岸も消える
後  窓の管 display=block path=4  ← 枠は外の岸が引き、中の岸の輪だけが残る
```

★ **逆（窓が枠も中の岸も自分で描く）は試して取り消した。** 継ぎ目の芯はつながったが、
  **窓の中の SVG は窓の外へ光を出せない**（器が切る）ので海の側が暗くなり、
  岸の継ぎ目も崩れ、もともと出ていたネオンまで消えた。枠は外が描くしかない。
  最後は「外が 1 枚で描く／中は輪を渡す」に落ち着いた（下の節）ので、この `frame` も消えた。

### そのほか

- **見え方の口の定位置は、上の縁の横の中間。** 中間は**サイドバーの幅を除いた残り**で測る
  ── 窓の真ん中で測ると、岸として塞がっているぶん左に寄って見える。
  横の中心は窓の幅から毎回出す（定位置は viewport を受け取る）。
- **迂回／枝分かれは窓の岸にも効く。** `WindowSpace` が `SpaceViewContext` から `join` を読む。
  見え方の口は 1 つしかないのに、窓の中だけ既定の「枝分かれ」に固定されていた。


### 窓を岸に貼ると、中身は作り直される

窓（空間を持つ泡）を岸に貼ると、中身は**別の場所で描き直される**（海の泡としてではなく、
岸の中身として）ので React は作り直す。そのままだと 2 つ壊れた:

1. **窓の中の岸が空になる** ── 貼ってあったものが消える
2. **`initialUrls` の種がもう一度まかれる** ── 同じ url の泡が 2 つ目として生える
   （実測：一覧が別にもう 1 つ出た）

岸は「窓の中身の一部」なので、**部品の一生より長く生きてよい**。名前（`persistKey` ＝ url）を
付けて器の外の棚に置き、作り直されたらそこから始める。種も名前ごとに 1 回だけにする。

名前が url なのは、**海にいても岸にいても同じものが取れる**から（岸は `d.url` から同じ
`RoutedBubble` を作り直す）。泡の id は剥がすと新しくなるので使えない。
同じ url の窓が 2 つあると岸を分け合うが、いまは url ごとに 1 つしか開けない作りなので成り立つ。

★ **窓の海そのものは、まだ覚えられていない。** 覚えているのは岸だけなので、貼り直すと
  海に浮いていた泡は消える（岸に貼ってあったものは残る）。海まで覚えるには
  `BubbleSpace` の世界と url の対応表を外へ出す必要がある ── **宿題**。

### 中身が自分の世界を持つ窓なら、管の帯を空けない

岸は貼ったもののまわりに**管の帯**（`TUBE_THICKNESS` ＝ 6px）を空ける ── 光をアプリの中に
入れないため。けれど窓の中身は**それ自体が岸を持つ器**なので、その帯は窓の岸が自分で使う。

空けていたころは、窓の中の岸が引く線が外の輪の 6px 内側に並び、**明るい芯が 2 本**に見えて
つながらなかった。

```
前  枠 266..826 / 174..790   中の海 272..826 / 180..784   ずれ 左6 上6 下6
後  ずれ 左0 上0 右0 下0                         ← 外の輪と中の線が重なる
```

見分けは `ground === 'clear'`（中身が自分で背景を持つ窓）。ランチャーやポケットの
`'none'`（地は中身が持つが、窓ではない）とは分けている。

★ 光が窓の中の海へ向かないのは、帯を空けなくなっても同じ（`keepOut` が中身ぜんぶを覆う）。
  **そのほうがよい**と決めた ── 外の岸の光が、窓の中の空へ差し込む筋合いは無い。


### 管の継ぎ目 ── 芯は相手を越える、抜く形も角丸

**芯が T 字でつながって見えない（まだ直っていない）。** 芯の端を `stroke-linecap: square` に
して中心線を半芯ぶん越えるようにはした（前は x=269 の 1 点だけで両方が当たっていたのが、
268.5 / 269 / 269.5 で重なるようになった）。`tubePath` の `stop` を増やす案は捨てた
── 「接している辺」と「通さない区間（迂回）」で**伸ばす向きが逆**で、1 つの値では両立しない。

★ **それでも見た目は直らない。** 継ぎ目の両側が**別々の SVG**にいるからで、
  重ねて描く限り白い芯は相手の青い帯に上書きされる（実測：14 倍で見ると、
  横の管が縦の管の帯の外側で止まっている）。

  分かったのは 2 つ:

  - 窓の中の SVG は**窓の外へ光を出せない** → **枠は外の岸が描くしかない**
  - 芯がつながるのは「帯を全部描いてから芯を全部描く」順序が効く**同じ 1 枚**の中だけ
    → **継ぎ目の両側が同じ SVG にいるしかない**

  そして**そもそも「輪を重ねる」のが間違いだった**。正しい言い方はこれ:

  > **ネオンは海そのものの形をなぞる。** 岸に着いたものは海から**切り抜かれている**。

  だから管は「箱の輪 ＋ 貼り物ごとの輪」ではなく、**引き算した形の縁を 1 本**で描く
  （`seaPath`）。形が 1 本なら、継ぎ目も角の突き合わせも**そもそも存在しない**（曲がるだけ）。
  帯も芯も同じ 1 本なので、芯を伸ばす細工（`joinAt` の調整、square キャップ）も要らない。

  描く場所も 1 つ: **いちばん外の岸が 1 枚で描く。中の海は、自分の海を親へ渡すだけ**
  （`TubeSinkContext`。器の位置ぶんずらして差し出す）。入れ子が深くなっても同じ規則で上へ渡る。
  こうして「窓の枠を誰が描くか」の場合分け（`frame` / `OnShoreContext`）は消えた。

```
外の岸  svg あり  芯 2本（外の海の輪郭 ＋ 窓の海の輪郭）
窓      svg 無し  芯 0本（海を親へ渡すだけ）
```

★ **ネオンの線に、閉じていない部分があってはならない。**

★ **大元の岸と、岸に着いた泡のあいだには線を作らない。** そこに水は無いので、囲うものが無い。
  その辺は**引かない辺**として渡し（`TubeSink.open` → `seaPath` の `open`）、線は
  **そこでちょうど終える**。終わり先は親の線と同じ点なので、合わせて閉じた形になる。

  ── 一度「二重に見えるのは岸に着いている合図」と読んで閉じたままにしたのは**間違い**。
  次に「その辺を外へ伸ばして追い出す」も試したが、**必ず行き過ぎて開いた端**ができた
  （実測：窓の上の線が外の海の線 823 を越えて画面の縁まで伸び、角が T に見えた）。
  伸ばすのではなく、**終える**。

```
外の海  … L 823 177 L 280 177 …        ← 823 で折れる
窓の海  M 269 188 A … L 823 177        ← 823 で終わる（右辺は無い）
        M 823 787 L 683 787 …          ← まっすぐ終わる（曲げない）
蓋      M 824.13 784 L 824.13 790      ← 帯だけ・太さ 2.25（青の片側と同じ）
```

★ **止める相手がいない端は、閉じて見せる。** 引かない辺の端の先が**別の岸で塞がっている**と、
  親の線が来ないので終わり所が宙に浮く。そこに**帯の太さぶんの短い線を直角に重ねる**
  （`seaCaps`）── 白い芯がその青に囲まれて、閉じて見える。

  - **本線は曲げない。** まっすぐ終わらせて、蓋は**別の線として重ねる**だけ
  - **蓋に芯は通さない。** 帯だけで描く ── 芯まで曲がれば、閉じて見せる意味が無い
  - **太さは、ハイライトを挟んでいる青の片側と同じ**（帯 6 − 芯 1.5 の半分 ＝ 2.25）。
    帯と同じ 6 にすると**少し太く見える** ── 続きの青ではなく、別の塊に見えてしまう
  - 置く所は**本線の端のすぐ先**（芯の端をちょうど塞ぐ）

  （「最後までのばす」も「端で線を曲げる」も試したが、前者は行き過ぎ、後者は線が曲がった。）

★ **決まるのは端ごと。** 辺ごとにすると、片方が塞がっているだけで反対の端まで効いて、
  親の線を通り越す（実測で踏んだ：上が 3px 行き過ぎて T になった）。

★ **角丸は海を削らない。** 丸めてよい角は 2 種類だけ:

  - **海が凹んでいる角**（貼り物の角が海に食い込む所）… 丸めると海が**増える**ので丸める
  - **箱そのものの 4 隅** … 器の角丸そのもの。削っているのではなく、海の形がそれ

  それ以外の**海が凸になっている角**（貼り物の脇で海が曲がる所）は、丸めると海が減るので
  **直角のまま**。輪を別々に重ねていたころは、引かない辺の隣が元から直角だったので
  ひとりでにそうなっていた ── 1 本にした拍子に、そこまで丸めて海を削ってしまった。

★ **差し出し口は毎回作り直さない。** render のたびに作ると、中の岸から見て「差し出し先が
  変わった」ことになり、輪を作り直す → 親が溜め直す → また render … と**止まらなくなる**
  （実測：Maximum update depth）。貼り物と窓の大きさが変わったときだけ作り、
  **同じ輪が届いたら溜め直さない**。

**角丸の外に暗い四角が残る。** 光を抜くマスク（`keepOut`）が**直角の矩形**のままだった。
中身の箱は角が丸いので、丸みの外側だけ光が抜けて暗い角が残る。抜く形にも丸みを付けた。

### 岸のロック ── スプリットビューは窓の大きさで崩れる

**岸で海を埋めた形（スプリットビュー）は、窓の大きさが変わると崩れる。**
岸の大きさは px で持っているので、広げれば**埋めていたはずの所に海が顔を出し**、
狭めれば向かい合った岸どうしが食い込む。
実測（窓 560x616 を 2 枚で埋めた状態 → 650x670 に広げた）:

```
継ぎ目  重なり 6px  →  隙間 84px（海が顔を出す）
下端    ぴたり     →  54px 開く
```

> **ロックした岸は、窓の大きさが変わっても海の分け方を保つ。**

引き直すのは**辺ではなく、管が通っている線**（`retileToViewport`）:

- 縁に着いている辺 … 新しい縁のまま（比では動かさない。縁は縁だから）
- それ以外の辺 … 辺を内側へ管の半分だけ寄せた所（＝線）を比で移し、半分だけ戻す

★ **辺そのものを比で動かしてはいけない。** 継ぎ目を分け合う 2 枚は管 1 本ぶん
  （`SHOWRE_DOCK_GAP` ＝ 6px）重なっているので、辺を別々に掛けて丸めると
  その重なりが 6 から離れる（倍率 1.5 で 9px になった）。**線は 2 枚で 1 本しかない**ので、
  そこを移せば両方が同じ答えになる。

★ **ロックを掛けた瞬間は何も動かない。** いまの形がそのまま「保つ形」になる。
  走るのは大きさが**変わったとき**だけ。

実測（ロック中、650x670 → 505x527 → 681x701）:

```
継ぎ目の重なり  6 → 6 → 6
四方の縁        0 → 0 → 0（ぴたり）
左の取り分      0.437 → 0.438 → 0.436
```

★ 口は**ステータスバーの × の隣**（`BubbleSpace` の `headerTools`）。枠は空間のもので、
  泡の中身からは触れない ── 「その泡そのものをどう扱うか」の口はここに差す。
★ ロックの持ち主は**窓より上**に置く。窓は岸に貼ると描き直されるので、
  窓の中に持つと貼り直すたびに外れる。名前は url（岸を覚える名前と同じ）。
★ **いちばん外の海はまだロックできない。** ステータスバーが無い（× も無い）ので
  口の置き場所が無い。ブラウザの窓を変えたときの崩れ方は同じなので、宿題。

### 一覧に coverflow を輸入する（ラボ v5-dom 場面 3）

一覧の行き先はこれまで 2 つだけだった ── **縦に並べて収まる**か、収まらなければ**奥行きに重ねる**か。
ラボにある並べ方をひとつずつ持ってくる、その 1 つめ。

```
coverflow:  x = 順序・等間隔・魚眼   y = なし・詰める・平行   z = なし・そのまま・平ら
```

プリセットそのものは最初から写してあった（`view.ts`）。要ったのは**使う所**の 2 つ:

★ **札の幅は、読める幅で頭打ちにする。** 詰める並びの札は「箱の中身いっぱい」なので、
  横長の箱では 532px にもなる ── そのまま横へ送ると**いつも 1 枚しか居られない**。
  頭打ちは既定の札の幅（`LIST_CARD_WIDTH` ＝ 392）。

★ **送り幅（等間隔の刻み）は札の幅に対する割合で決まる。** プリセットが持っている 68 は
  ラボの写真（幅 90）に対する値なので、札が 392 だと**3 枚がほぼ同じ所に重なる**（実測で踏んだ）。
  比はラボと同じ 68/90 ＝ 0.756 ── 札より少し狭いと、隣が肩を出して「まだ後ろに居る」が見える。

実測（窓の岸に貼った一覧・板 560x226・3 枚）:

```
column     札 532  translate(14, 97) (14,185) (14,273)  倍率 1
coverflow  札 392  translate(16, 91) (111,72) (376,91)  倍率 0.43 / 0.86 / 0.43
```

★ **「並べ方が当たっているか」は、並べ方が決めるもの（次元・並べ方・レンズ）で見る。**
  刻み・隙間・取り分は**当てたあとで外から合わせる値**なので、そこまで見比べると
  合わせた途端に「プリセットと違う」になり、**当て直しが止まらなくなる**
  （実測で踏んだ：刻みを札の幅から決めた瞬間に Maximum update depth）。

★ **選び方の条件は仮。** いまは「縦に収まらない ＋ 箱が横長なら coverflow、縦長なら奥行き」。
  ラボの並べ方を**全部輸入してから、条件ごと整理し直す**（2026-09-24 の申し送り）。

### 縦の coverflow（輸入 2 つめ）

**coverflow の X と Y を入れ替えただけ。足した仕掛けは 1 つも無い。**
順序を縦に等間隔で置き、Y に魚眼を掛ける。横は「なし・詰める・平行」＝ 箱の横の中央。
ラボ（v3 の 06-layout-apart）が「作れる。足すもの無し」と数えていたのがこれ。

```
coverflowY: x = なし・詰める・平行   y = 順序・等間隔・魚眼   z = なし・そのまま・平ら
```

★ **送り幅は「送る向きの辺」で測る。** 横へ送るなら札の幅、上下へ送るなら札の**高さ**
  ── 欲しいのはどちらも「札より少し狭い」なので、比（0.756）は同じ。
★ **どの軸に当てるかは、その軸が「等間隔」を刺しているかで決まる**（`equalAxisOf`）。
  軸の名前を書かずに済むので、次に輸入する並べ方でもそのまま効く。
★ **札は箱いっぱいのまま**（横は細くしない）。送るのは上下なので、幅を削る理由が無い。

実測（窓の岸に貼った一覧・3 枚）:

```
板 560x304（横長）  札 392  y=130 / 111 / 130   倍率 0.43 / 0.86 / 0.43
板 223x304（縦長）  札 189  y= 55 / 106 / 171   倍率 0.82 / 0.97 / 0.82
```

★ **`stackDepth`（奥行きに重ねる）は、いまの条件では出番が無い。** 消してはいない
  ── 選び方を決め直すときに、もう一度机に乗せる。

### 折り返す coverflow（輸入 3 つめ ── 2 行以上で並べる）

```
coverflowGrid: x = 列・等間隔・魚眼   y = 行・等間隔・魚眼   z = なし・そのまま・平ら
```

★ **軸に刺すのは順序ではなく「列」と「行」。** 順序を 2 行以上に折るには、
  軸が 2 つとも「順序」を読んでいては足りない ── 同じ値を両方が読むので、
  斜めに一直線に並ぶだけになる。折った結果（列・行）は**泡が持つ**（`cell`）。

★ **どこで折り返すかは、View（見え方）ではなく並べる側が持つ。**
  「箱に何枚入るか」は箱の話であって見え方ではない。View に持たせると、
  同じ見え方を別の大きさの箱で使えなくなる。一覧は `colsFor` で数え、
  `setChildren` に列数を渡す ── 受け取った側は**順序から `cell` を書き直すだけ**
  （`cellsOf`：`col = 順序 % 列数` / `row = 順序 ÷ 列数`）。並べ方は読むだけ、の形は崩さない。

★ 送り幅は**両方の向き**に要る（横は札の幅、縦は札の高さ。比は同じ 0.756）ので、
  `stepFor` は軸ごとの組を返すようにした。`setChildren` の引数も 6 つに増えていたので、
  **どう並べるかを 1 つの物**（`ChildrenLayout`）にまとめた。

★ **選ぶのは「縦にも横にも 2 枚以上とれるとき」**（仮）。
  1 列・1 行に押し込むのは、押し込むしかないときだけ ── 折り返しを先に見る。

実測（窓の岸に貼った一覧・3 枚・札 392x88）:

```
板 828x226  折り返す coverflow  列数 2  (132,45) (366,45) (132,101)  倍率 0.84
板 828x402  縦に並べる（収まった）      (14,66) (14,154) (14,242)   倍率 1
```



### 札の幅は「名前が何文字入るか」── 理想 12・下限 7

> **理想は 12 文字。箱が足りなければ 7 文字まで譲る。**
> **12 文字を超えるのは、12 文字より長い名前があり、かつ箱に余地があるときだけ。**

札の中身のうち幅を決めているのは**名前の行だけ**（`9路 対局` は 47、`2手・対局中・黒番` は 103、
名前は 12 文字で 156 ── 実測）。だから札の幅は「名前に何文字ぶん割くか」の 1 つで決まる。

```
札の幅 ＝ 152 ＋ 文字数 × 13
  152 ＝ 余白10 ＋ 盤64 ＋ すき間10 ＋ アイコン18 ＋ すき間10 ＋ ×の口30 ＋ 余白10
   13 ＝ 全角 1 文字（13px）
```

★ **縮むのは箱が足りないときだけ。** 名前が短いからといって細くしない
  ── 並んだ札の幅が名前の長さでばらつくと、一覧が読みにくい。
★ **文字数は全角 1 文字で数える。** 実際の字を測ると、名前を書き換えるたびに札の幅が動く。
★ 下限を割る箱では、**7 文字のまま見切れさせる**（縮め続けない）。岸で決めたのと同じ。
★ 札は「箱にこれだけ空いている」を受けて**自分で**幅を答える（`ListSpace` の `itemWidth` は
  数でも関数でもよい）── 譲る規則を持つのは箱ではなく札のほう。

実測（囲碁の一覧・いちばん長い名前 15 文字）:

```
並びに使える幅 378  →  15 文字 347   余地があるので 12 を超えて伸びる
             344  →  14 文字 334   余地のぶんだけ
             212  →   7 文字 243   下限で止まり、箱からはみ出す（見切れる）
名前が 12 文字以下  →  12 文字 308   箱がいくら広くても理想のまま
```

### 箱 ＝ 中身 ＋ 装い（`chrome.ts`）

> **泡が持つ大きさは、中身の大きさ。枠は自分のぶんを外へ足す。**

前は泡の `size` が**装い込みの箱**だった。だから同じ札が、置かれた場所で**中身の大きさまで変わって**いた:

```
              枠が取る上下      札 120 のときの中身
海に浮いた泡   27 + 7 = 34       86
一覧の札（静か） 1 + 1 =  2       118
```

札の高さを海に合わせると一覧で 34 余り、一覧に合わせると海で見切れる ── **どちらを選んでも破綻する**。
そしてこの一点から、その場しのぎが 4 つ生えていた:

```
SELECTED_GROW = (27+7)−(1+1)     選んだ札だけ背を伸ばして中身の高さを保つ
toDockSize / toBubbleSize        岸へ貼るとき 24 引き、海へ返すとき 24 足す
「札の高さ＝中身＋34」の慣習       MEMO_CARD・IGO_CARD・CARD の註
模型のヘッダ 24 と CSS の 27      3px のずれを一覧の口の隙間に込める
```

**4 つとも消えた。** 装いの表（`CHROME`）を 1 つ置き、模型（`measureBox`）も CSS（`.bl-body` の inset）も
そこを読む。どの装いを着ているかは**そのフレームだけの話**なので、世界には書かず `ChromeMap` で渡す
（② 触っても値は 1 つも書かない、を守ったまま `SELECTED_GROW` の役目が果たせる）。

```
bare   0 / 0  / 0 / 0     ③ 見えない親、岸に着いた泡
bar    0 / 24 / 0 / 0     帯だけ。窓と**ラボの泡**。模型の既定
plain  7 / 27 / 7 / 7     普通の泡
quiet  7 /  7 / 7 / 7     一覧の札（装いを出していない）
packed 7 /  1 / 7 / 1     一覧の札・縦に詰める並び
```

★ **既定が `bar` なのは、模型の素の振る舞いをラボと同じに保つため。** 左右や下の余白は
  「バブリの画面を載せる器」の都合で、模型そのものの性質ではない。ラボの場面の数は箱で
  書かれているので、**入口（`labScene`）で帯 24 を引く** ── 解いたあとの箱はラボと 1px も違わない（78 本緑）。

実測（囲碁の札。中身は 308×84 のまま動かない）:


### 触ったら選ぶ。掴めるのは枠だけ

> **枠の高さは、その泡が着ている装いから取る**（固定の 24 ではない）。
> **中身を触っても選ぶ。掴んで動かすのは枠だけ。**

当たり判定（`hit.ts` の `inContent`）が**固定の 24px** を枠として見ていたので、
装いの表（`chrome.ts`）を作ったあとも、そこだけ古いままだった。実測:

```
対局の泡（箱 473）  選べるのは上の 24px ＝ 5%
一覧の札（箱 86）   上の 24px が枠扱い ＝ 28%
                    名前の行 13〜33 の**上半分**と、盤のサムネイル（11〜75）の上 13px がそこ
```

大きい泡は「枠が細すぎて選べない」、札は逆に「枠が中身を食っている」── どちらも同じ 1 行から。

★ **静かなのは「一覧の中に居て、選ばれていないとき」だけ。** 装いは泡の性質ではなく、
  **置かれた場所と、いま相手にされているか**で決まる ── 海なら装い、岸なら装い無し（`bare`）、
  一覧の中なら静か。触れば泡として立ち上がる（消しているのではなく、静かにしているだけ）。

★ **選んだ札は装いを出す。** 一度「輪だけにして何も動かさない」形にしたが、
  **薄い膜のままの札はやめる**という判断で戻した（2026-09-24）。
  装いが出るぶん箱は 32 伸び、**並びの後ろの札はそのぶん送られる** ── 中身の大きさは変わらない。

## 言葉づかい

**「軸に次元を刺す」は僕（Claude）の造語で、日本語として変だった。**
正しくは「**その軸が読む値を選ぶ**」。泡は `free` `order` `cell` `hist` を持っていて、
空間の View は軸ごとに「どれを読むか」を1つ選ぶ。`order` は泡に1つしかないので、
同じ空間の中で X と Z の両方が読むと連動してしまう ── というのが「取り合い」の中身だった。
