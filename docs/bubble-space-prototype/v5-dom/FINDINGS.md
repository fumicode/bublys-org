# DOM 版はいけるか ── 5案を同じ台で測った

仕様は `../v4/RULES.md`（正）。台は `bench/README.md`。
**数字はすべて実測**（各案の担当 ＋ 独立の検証者。1440×900・dpr1・Chromium 145 headless・3回の中央値）。
**★ は独立の検証でひっくり返った所。** 隠さず全部出す。

---

## 1. ひとこと結論

**DOM でいける。** 5案とも3場面すべてで落ちたフレーム 0、矩形は解いた答えと 0.0001px 以内、絵は canvas と見分けがつかない。
ただし「canvas の 9〜12倍速い」は**主スレッドだけの話**。実時間で本当に勝つのは魚眼の場面だけ（2.2倍）。DOM は仕事を減らしたのではなく、ラスタを別スレッドへ出した。
**masa さんの「動かすあいだは画像」は、いまの泡（箱＋題名1行）では要らない。** 中身が重くなったら効く ── 既存 bubbles-ui では実測 2.2倍。

| ホイール60フレーム | 場面A | 場面B | 場面C |

### ★ masa さんの「画像でキャッシュ」はどうだったか

**4通りに分けて測った。効いた場面と、引っかかった所がはっきり分かれた。**

| やり方 | 結果 | 引っかかった所 |
|---|---|---|
| **① 泡ぜんぶを1枚の PNG アトラスに焼く**（image-cache.html） | **work は本物に速い**（場面C のホイールで canvas の 1/12）。実機でも場面C は 24.9ms→8.3ms（**40fps→120fps**）の本物の勝ち | **★ 魚眼でドラッグすると焼いた絵が 5.9倍に伸びて題名が消える**（絵が嘘をつく）／**★ 実機で冷たいまま掴むと 50.4ms 止まる**（焼き 167.6ms）／箱が変わるたび **全521個を焼き直す**（台本1巡で 2〜3回）／Retina は k=2 が要り アトラス 36MB・焼き 144ms／**実機では場面A も場面B も canvas がすでに 120fps を保っていて引き分け** |
| **② 泡ごとに SVG data URL を焼いて background にする**（hybrid の ④） | **効かなかった。**ホイールは誤差（A 0.4→0.4 / B 2.3→2.2 / C 0.8→0.9） | 大きさ変えが **1.6〜3.8倍おそい**（箱が変わる泡を毎フレーム焼き直す：120フレームで A 240回・B 360回）／heap 10.6→40.8MB（**4倍**）／最初の1枚が場面C で 4.9倍 |

**読み方：画像キャッシュが効くのは「1つの泡の中身が重いとき」。** いまの v5 の泡（箱＋題名1行）では中身が軽すぎて、焼き代のほうが高い。

**だから「いまは要らない、中身が重くなったら戻ってくる話」。捨てる話ではない。**

### ついでに分かった、masa さんの前提のもう一つの訂正

> 「DOM での scale はけっこう重い」

**測った限りでは逆だった。** 58個を全部動かして

| 書き方 | 1フレーム | CDP の Layout |
|---|---|---|
| `transform: translate` だけ | 0.088ms | — |
| `transform: translate() scale()` | **0.164ms** | **0.0006ms（ゼロ）** |
| `left/top/width/height/font-size` を書く | **0.772ms（9倍）** | **0.170ms** |

**重いのは scale ではなく px レイアウト。** 実際、全案で一番大きな事故はここだった ── 字の下限 4px を `font-size` で毎フレーム書いた版は、場面C のホイールで layout 1951ms（33ms/フレーム）・落ち 50。同じことを `transform` でやれば layout は 0。
（ただし headless はソフトウェアラスタ。**scale 変更による GPU テクスチャの焼き直しだけは測れていない** ── 実機での測り直しが要る。次にやること④）

## 3. 推奨する描き方 ── `hybrid.html`（平ら＋飛ばす＋字の逆 scale）

`docs/bubble-space-prototype/v5-dom/bench/hybrid.html`

**中身は3行で言える。**
1. 泡を全部 `#stage` の兄弟にする（DOM の入れ子にしない）。要素の素の大きさは箱（bw×bh）のまま
2. 毎フレーム書くのは `transform: translate() scale()` **1行だけ**。ドラッグする・ホイールで layout が 0
3. 画面で固定の量（枠 1px・字の下限 4px）は、**逆 scale を当てて戻す**。`border-width` や `font-size` では絶対に書かない

### なぜ nested（入れ子）ではないか ── 速さではなく、規則で落ちた

入れ子のほうが数字はわずかに良い（C ホイール 1.3 対 1.5ms）。落としたのは**規則②**。

> **②「触った泡は手前へ」が、入れ子の DOM では表せない。**
> transform を持つ div は必ず重なりの文脈を作るので、子は「親の兄弟」の上には出られない。
> 実測：場面A で「制約」（勤務表の子）を掴んで「議事録」の上へ運ぶと、canvas では制約が手前、nested では議事録が手前。重なり 242×65 の中で 688画素が食い違う（`evidence/入れ子DOMで規則2が破れる.png`）。
> 平らなら 202個すべてで `z-index` ＝ 描く順 が一致した（食い違い 0）。

しかも「奥の泡を掴んだら木から外して root 直下へ移す」で逃げると、その瞬間だけ入れ子の考え方を捨てることになる。
**規則のほうが数字より上。だから平ら。**

台のほうも同じ答えを出している ── v4 の契約の実測で、**合成は `resolveSpace` で1回きり・scale は数値1つ**なので、平らに置いた58要素は canvas と最大 0.015px しか違わず、当たり判定も 1209点中 1192点一致した（食い違い17点は見えない親の縁と丸め）。

### ★ 足したのではなく、足さずに済んだもの

masa さんの「懸念その2」への答えは、ほとんど**引き算**になった。

| 足さずに済んだもの | なぜ要らなかったか（実測） |
|---|---|
| **DOM の入れ子** | 合成は解く所で1回きり。平らで矩形が 0.0000px 一致。むしろ入れ子だと②が壊れる |
| **画像キャッシュ** | いまの泡では焼き代のほうが高い（上の表）。中身が重くなったら戻る |
| **`will-change` / レイヤ昇格** | 数で効き方が裏返る（202個では効く、521個では落ちフレームが増える）。既定にできない |
| **自前の LOD（小さい泡を簡略に）** | 丸めるだけで同じ速さ（C 1.5 対 1.2ms の差しかない）。しかも LOD は絵を割る |
| **仮想化・切り抜き（`contain:paint` / `content-visibility`）** | **規則が禁じている。**実測で4種類すべて子を切った（150px 外の子が取れなくなる）。使えるのは `contain: layout style` と `will-change` だけで、どちらも速くならなかった |
| **`font-size` の毎フレーム書き換え** | これが場面C の layout 1951ms の犯人。`transform` に移すと 1.6ms |
| **並べ替えの毎フレーム処理** | `z-index` は描く順の配列番号をそのまま入れるだけ。実測で順番が変わったのはドラッグする61フレーム中 1〜2フレームだけ、ホイール中は 0 |

**足したのは2つだけ ── `transform` 1行と、題名の逆 scale。**

### 推奨の絵の正しさ（実測・独立検証で小数点まで一致）

- 矩形 対 解いた答え：場面A **0.0000px** / 場面B **0.0000px** / 場面C **0.0001px**（泡 58・521・202 すべて）
- 画素：canvas との差>8/255 が A 2.56% / B 9.09% / C 1.53%、平均ずれ 1.378 / 4.096 / 0.514
  → **素朴 DOM（3.28% / 12.15% / 2.89%）より canvas に近い**
- 5〜8倍に拡大して目視：配置・色・角丸・枠・重なりの上下・題名の位置が一致
- 残る差は 字のアンチエイリアス ／ 枠が中心線か内側か（canvas の 1px stroke は2画素、DOM は1画素）／ 見えない親の破線の刻み

### 推奨のまま残っている破れ（隠さない）

1. **画面の px を1つでも毎フレーム書いたら、そこで全部終わる。** いまは「箱の座標で持ったものは倍率が変わっても書く値が変わらない」ことだけに乗っている。本物の泡に髪の毛線・最小文字サイズ・画面幅で変わる並びが1つでも入れば layout が戻る
2. **中身が本物になった瞬間に崩れる。** いまは箱＋題名1行なので scale が効く。文が折り返す・入力欄・画像が入ると、scale は組み直さずラスタを引き伸ばす（0.3倍では読めない）
3. **数が増えると負ける向き。** 58個で canvas の 0.11倍 → 521個で 1.18倍に反転した。折れ線の交点は 202〜521個のどこか。**1000個超は誰も測っていない**
4. **画面外の泡を捨てる手が全部使えない**（切り抜き禁止）。3場面とも画面の中が 100% なので、**この弱点は一度も試されていない**
5. **平らにすると DOM の親子が消える。** CSS の継承・イベントの伝播・読み上げの入れ子が効かない。泡の中に入力欄を作るときは別の手当てが要る
6. **大きさ変えだけは layout が残る**（箱が変わるので width/height を書く）。場面B で 14.6ms/60フレーム

### 推奨：**B 動詞**（ただし決めるのは masa さん）

理由は3つ。全部この張りぼてで実測した。

1. **降りる道と戻る道が、操作子を増やさない。**「詳しく ▾」を開くと、閉じているとき読み取り専用で出ている 3×3 の表がそのまま select 9個になる。**画面の形が変わらない**ので、どのセルが何だったか目で追える。戻り道は自動 ── 9つの値が動詞と一致した瞬間ひとりでに動詞名へ戻る（実測：X を 履歴の古さ にすると「手直し中」、順序 に戻すと「並べる（横）」へ復帰）。**「動詞へ戻す」ボタンが要らない**
2. **閉じた型ではない。**動詞は View の別名＝表の1行なので、C が「札にできない」と落とした**「重ねる」が1行で出る**（Z＝順序·等間隔·透視、実測）
3. **いま選んでいるものが v4 のどれかが常時見えている**（例：＝ v4 lab.html の PRESETS.row）。隠したものが何なのか、開かなくても分かる

**足すならこの順で。**C の「中身が答えられない次元は灰色にして理由を出す」は、動詞にあとから足せる（A の弱点2「名前が嘘をつく」がこれで潰れる）。逆は難しい。
見えている操作子は v4 の 19個 → **3個**。ただし**押す手数は減っていない**（v4 もプリセットは1押し）。減ったのは画面に出ている数。

## 5. 既存 `bublys-libs/bubbles-ui` をどうするか

### 結論：**載せ替え（描く所だけ差し替え）は無理。先に規則の食い違いを埋めないと二重に動く。**

食い違いを**先に**出す。上ほど大きい。

| | 既存 | v4 の規則 | どうなるか |
|---|---|---|---|
| **1. 重なりの上下** | `process.layers: string[][]`（配列）＋ 同レイヤー内は置いた順。フォーカスで最後尾へ移動、さらに z-index 100 直書きでレイヤーを飛び越える | 「描く順は dz → scale → 並び順。**View の外の状態は持たない**」 | **ここが一番大きい書き換え。**レイヤー配列を捨てて、泡側に `free.z` / `order` を持たせる所から |
| **2. 泡が持つ値** | `position` と `size` だけ。`free.z` `order` `cell` `hist` に当たる値が無い。**Z は「どの配列に居るか」でしか表せない** | 泡が値を持ち、View が読む | 泡のデータ構造から作り直し |
| **3. 並べ方** | 測った矩形から次を決める（`SmartRect.calcPositionForSibling` が 右→下→左→上 に空きを探す）。**測る→Redux→再レンダ→また測る のループを持つ** | ④ 帯の式。値から純粋に計算する | ループが要らなくなる代わりに、`renderedRect` に依存する `joinSibling` `popChild` 世界線の除外処理がまとめて不要になる。**中途半端に両方残すと二重に動く** |
| **4. 倍率の式** | `scale = 1 − layerIndex × 0.1`（線形減衰）。**10 で 0、11 以上で負。クランプ無し**（実測：`scale(-0.1)` は消えずに鏡像で出た） | 透視 `m = 1/(1 + 0.26·dz)`、**dz<0 は消す** | layerIndex→scale の対応が全部ずれる |
| **5. その式のコメントが嘘** | `CoordinateSystem.ts:49-59` のコメントは「1→1.0、2→0.9」だが `Math.max(0, i − 1 + 1)` は結局 `i` なので実際は **1→0.9、2→0.8**。`SCALE_START_LAYER_INDEX` は効いていない | — | **コメントを信じて移植すると1段ぶん狂う** |
| **6. 入れ子** | universe 泡（窓）だけ真の DOM 入れ子。scale が積になるのを `bbcr.width / offsetWidth` で**測って戻している** | scale は数値1つで、合成は1回だけ | v5 の答え（平ら＋自分で合成）が素直。測り戻しは丸ごと捨てられる |
| **7. 箱の伸び** | 全泡に `max-height: 90vh` が直書き（`//FIXME:突貫対応`） | ④「`equal`/`pack` の軸では箱が中身まで伸びる」「切り抜きはしない」 | 正面衝突 |
| **8. 同じ空間の二重描画** | 既に地雷が実測済み。世界線 hook が2つ走り url を書き換え合うので、`universeDrivers` Map で先にマウントした1つだけを駆動役にして回避している | v4 は「奥のレイヤーに同じ空間の縮小コピーを出す」 | **正面から踏む** |

### おまけ：既存で測って分かった、直しても効かない所

- `will-change: transform` は無風（窓 22→22 frames）
- 親1枚に scale は**むしろ遅い**（120回 107 frames 対 親1枚 95 frames）
- `left/top` → `transform` の定番の書き換えも**ここでは逆に遅い**（72→57 frames）。`position:absolute` の泡は兄弟に影響しないのでレイアウトが元から安い
- **詰まっているのは主スレッドではなくラスタ。`backdrop-filter` が単独で 7倍効く**（120泡で 152→22 frames/2s）。窓の見た目を v4 に持ち込むなら、**ここを最初に削るのが一番効く**
- `transition-property: left top transform;`（空白区切り）は**無効構文で `all` に落ち**、次行のショートハンドが再び `all` に上書きしている。結果、4段グラデ・影4枚・`backdrop-filter` まで全部 0.3s でアニメしている。**書き写すときに一緒に持ち込みやすい**

### 三択（決めるのは masa さん。→ 6章）

いまの実測から言えることだけ書くと：**1〜3 が「描く所の差し替え」では埋まらない**ので、「載せ替え」は選べない。
残るのは **作り直し** か **共存**。

## 6. masa さんに決めてほしいこと

### 決めごと1：**泡は拡大するのか。それとも縮むだけか**

**これを先に決めないと、案が選べない。** 今の3場面は**一度も拡大していない**（ホイール往復160フレームすべてを見て、見えている泡の最大倍率は A 1.0044 / B 1.000 / C 0.978）。
つまり masa さんが気にしていた「拡大したときの字の粗さ」＝画像キャッシュの一番の弱点は、**この台では一度も試されていない**。

| | 何が起きるか |
|---|---|
| (a) **縮むだけ**（レンズは縮小専用、焦点より手前は消す） | いまの測定がそのまま使える。画像キャッシュも成立しうる |
| (b) **2倍まで拡大する** | 画像キャッシュは落ちる（実測で 5.9倍まで伸びて題名が消えた）。hybrid は最大倍率 1.116 まで確認済みで字がぼけない |
| (c) **青天井**（寄り続けられる） | 焼いた絵は使えない。字は必ず組み直しが要る。枠の逆 scale も `scale ≤ 2/bw` で壊れる（実測） |

### 決めごと2：**「枠は画面 1px」「字は下限 4px」という画面固定の量を、規則として残すか**

**これが入れ子の得を消していて、平らでも代金を払っている所。**

| | 代金（実測） |
|---|---|
| (a) **残す**（逆 scale を書き戻す。推奨案はこれ） | 場面B のホイール 1.3→2.7ms（+1.4ms/フレーム、style 2.4→52.4ms）。場面C でも 0.7→1.3ms |
| (b) **捨てる**（枠も字も泡と一緒に伸び縮み） | **倍速い。**ただし倍率 0.12 の泡は枠が 0.12px になって消え、題名が 1.4px の滲みになる（canvas と絵が違う） |
| (c) **枠だけ残す**（inset box-shadow は layout 0）／字は 0.5px 刻みに丸める | 丸めだけで C 1.5ms。**題名を1つも捨てずに canvas の 6.7〜8.9倍。**代金は「ズーム中に字の大きさが階段で跳ねる（最大 12.5%）」 |

### 決めごと3：**既存 `bubbles-ui` をどうするか**

| | 中身 |
|---|---|
| (a) **作り直し**（v5 のレンダラを土台に、既存から拾えるものだけ拾う） | 5章の食い違い1〜3を正面から直す。既存の「測る→Redux→再レンダ」ループと `renderedRect` 依存が丸ごと消える |
| (b) **共存**（v5 は新しい空間だけ。既存はそのまま残す） | 一番安いが、重なりの上下（`process.layers`）が2つの世界で別々に動く |
| (c) **載せ替え**（描く所だけ差し替え） | **実測から見て選べない。**Z の持ち方と並べ方が食い違っているので、描く所だけ替えると二重に動く |

## 7. 次にやること（順番に）

1. **拡大する台本を1つ足して、3案（hybrid / image-cache / 字の作り方）を測り直す。**
   いまの3場面は倍率の上限が 1.00 で、**縮む側しか通っていない**。決めごと1 の材料がここで初めて揃う
2. **`placements()` に `vis` を足す。**
   実測で `alpha 0.640`・`scale 1.16` で**見えているのに掴めない**泡がある（canvas の hitTest は `alpha` ではなく `vis` を見ている）。`opacity` と `pointer-events` を同じ数から作ってはいけない。**DOM 版の第一歩はここ**
3. **見えない親（③）を DOM で作る。**
   実測で箱の中は空洞、当たるのは**箱の外 12px の縁だけ**。div 1枚では表現できない（`clip-path` は切り抜きの罠）。`pointer-events:none` の枠＋4本の縁ストリップ。3場面はどれも見えない親を1個しか持たず、当たり判定は `placements` 任せだったので**まだ一度も作っていない**
4. **実機（M1 Max・dpr2・120Hz）で hybrid を測り直す。**
   headless は rAF 8.3ms（≒120fps）でソフトウェアラスタ。**scale 変更による GPU テクスチャの焼き直しだけは測れていない。**ここで `will-change` を入れるか（ラスタ 2〜10倍 対 字のにじみ）も決まる
5. **泡の追加・削除・親の付け替え（落とし込み）を書く。**
   5案すべての雛形が「`render` は最初の1フレームだけ・`update` は親子を見直さない」になっている。台本が落とし込みを外してあるので**一度も試されていない**が、本物の UI では必ず要る（付け替えたフレームだけ layout が出る）
