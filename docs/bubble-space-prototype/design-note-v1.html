01

中心のルール

公理

泡の画面上の見え方は、論理座標 (x, y, z) と レンズ の合成だけで決まる。それ以外の特別扱いを一切しない。

現行 bubble-ui では「レイヤー配列の何番目か」「フォーカスされているか」「universe かどうか」「最大化か」が、それぞれ別の経路で見た目に効いていた。この4本を1本にまとめる。個々のイベントハンドラで挙動を書くのではなく、この1文から挙動が導出される状態を目指す。

そこから2つの操作ルールが自動的に出てくる。

操作

自由な次元を束ねた軸では、泡が動く

ドラッグ量を局所倍率で割った分だけ論理座標が動く。従来の移動。

操作

データの次元を束ねた軸では、焦点が動く

同じ横ドラッグが、履歴軸に束ねれば履歴のスクラブになる。

03

解決の経路

1つの泡が画面のどこに何倍で描かれるかは、2つの経路のどちらかで決まる。拘束する関係を持つ泡はホストのアンカーから、持たない泡は次元とレンズから。

04

関係と配置

分離

関係は意味、結合は配置。関係が配置を拘束するかどうかは、2段階しかない。

「開いた」を拘束にしてはいけない

いちど「開いた」を 奥行きだけ拘束する 中間段階（bind:"depth"、ゲストの z を host.z − 1 に固定）として設計したが、これは二重に間違っていた。

  • 永続的な拘束ではない。 開いた泡はあとから奥へ送ってよい。参照しながら別の作業をするときに背後へ回す、というのはごく普通の操作で、拘束はそれを禁じてしまう。
  • そもそも host.z − 1 ではない。 現行の popChild は layers.unshift([id])、つまり opener がどこにいようと最前面に置く。opener との相対位置ではない。

正しくは、「開く」は関係の性質ではなく操作。その瞬間に最前面へ置き、関係のほうは出来事として残るだけでよい。

kindbind帯引き剥がしたとき
含むplaced塗り関係も消える
隣り合うplaced接する辺が光る関係も消える
開いたnone塗り—（そもそも拘束していない）
参照none糸—
由来none糸—
注釈none糸—

placed の2つは配置そのものが意味なので、泡を引き剥がせば関係も消える。それ以外は配置に触れていないので、引き剥がすという概念がない。

不変条件。 1つの泡が持てる placed 拘束は高々1つ。拘束しない関係はいくつでも持てる。この不変条件は呼び出し側ではなく、索引を張り直す reindex() が担保する。

関係グラフは軸に刺さる

次元は関係グラフを遡って深さを数えられる。どの kind を辿るかはパラメータで、拘束するかどうかとは無関係。だから拘束しない「開いた」も軸に刺せる。

chainDepth(bubble, kind)   // その種類の関係を遡った鎖の長さ

open.chain     = −chainDepth(b, "opened")     // 開いた連鎖。深いほど手前
contain.chain  =  chainDepth(b, "contains")   // 入れ子の深さ

現行の openDepth は open.chain に一般化される。ここで軸の仕組みと関係の仕組みが噛み合う。

05

アンカーの3種

規則

アンカーがホストの内側にあれば、ゲストはホストの座標系に入る。外側にあれば、ゲストは自分の奥行きのまま、画面上で辺が接するだけ。

中に入るのと隣に並ぶのは、幾何的に別物だった。前者は座標系の入れ子、後者は画面上の接触。隣接がホストの縮尺を継承してはいけないのはこのためで、継承させると「リストの隣に、リストより手前でアイテムを大きく開く」が書けなくなる。

アンカー座標系縮尺大きさホストを押し広げるか
hole(rx,ry,rw,rh) ホストの中身座標系
自前サイズの比率		 ホスト由来 枠が決める しない
seat(x,y) ホストの中身座標系
中身座標の絶対値		 ホスト由来 ゲスト自身 押し広げる
beside(side,gap) 画面上の接触
辺どうしを合わせる		 ゲスト自身の z 由来 ゲスト自身 しない

用途はそれぞれ、hole が表のセルやパネルの一角と中身の中のリンク、seat が後から放り込まれた泡、beside が隣り合う泡。

すき間の尺度。 beside の gap はゲストの縮尺で画面 px に落とす。ゲストが奥へ行くとすき間も縮む（14px → 8px）。「すき間はゲストの世界に属する」という解釈だが、ホスト側の尺度や固定 px のほうが自然な場面もありそうで、まだ決め切れていない。
06

結合の力学

結合は静的な設定ではなく、4方向に働く力になった。すべて毎フレーム解かれる。

ホスト → ゲスト

アンカーが位置と大きさを決める

ホストが縮尺を持てばゲストもその縮尺に乗る。穴ならゲストの大きさも枠が決める。

ゲスト → ホスト

席が場所を要求し、箱が伸びる

必要な箱幅 = 席x + ゲスト幅 × depthMag(dz) + 余白。手前に浮くほど広い場所が要る。

兄弟 ⇄ 兄弟

席が場所を譲り合う

重なりが最小の軸へ押し出す。ホスト自身の中身も場所を取るもののひとつとして同列に扱う。

近接 → 結合

近づけると関係が生まれる

縁の帯に触れれば隣り合う、帯より内側まで入れば含む。膜に触れれば隣接、中まで入れば包含。

3つ目の「ホスト自身の中身も場所を取る」が、放り込まれた泡がホストの中身を隠さないという要求を特別扱いなしに満たす。中身が場所を占めているので、後から来た泡は自然にそこを避ける。

08

13の制約

すべてプロトタイプで実際に踏んだもの。設計を書いた時点では見えていなかった。実装時に同じ穴を掘り直さないための記録なので、番号で参照する。

  1. 01
    消失点は焦点と別に持つ。 一致させると奥の泡が手前に完全に隠れる。式は screen = VP + ((center + (p − focus)) − VP) × mag。現行 CoordinateSystem.vanishingPoint が効いていたのはこれが理由だった。
  2. 02
    焦点より手前は倍率が発散する。大きくし続けず、透明にして消す。 1/(1+k·dz) は dz → −1/k で無限大。alpha = clamp(1 + dz×0.55, 0, 1)。
  3. 03
    焦点の奥行きは既定で「一番手前の泡」に合わせる。 制約 02 と対になる。開いた泡が手前に来るのに焦点が奥のままだと、フェードが効いて開いた泡が半透明になる。現行 bubble-ui は常に最前面を見ている。
  4. 04
    次元には向きがある。 「履歴の世代（大きいほど新しい）」を奥行きに刺すと過去が手前に来る。奥行き用には「履歴の古さ」という別の次元が要る。
  5. 05
    穴は自前サイズの比率、席は絶対値。これが唯一安定する組み合わせ。 両方を比率にすると「成長 → 比率アンカー拡大 → 再衝突 → さらに成長」で発散する。逆に穴を伸びた後のサイズの比率にすると、伸びた分だけ穴が広がって中身が破綻する。
  6. 06
    ホストを押し広げるのは席だけ。 穴（ゲストが枠に従う）と隣接（外側）に要求させると、制約 05 の発散を引き起こす。
  7. 07
    ホスト自身の中身は「自前サイズ」の範囲にだけ描く。 伸びた分まで中身を広げると、せっかく席を外へ押し出しても中身が下に潜り込んで隠れる。
  8. 08
    押し出し方向は「左上より外へ出さない」制約付きで最小移動を選ぶ。 これがないと負座標が生まれ、ホストの原点が動いて全体がずれる。書き戻しは減衰 0.35 で滑らかに落ち着かせる。
  9. 09
    隣接には「辺に沿った並び順」が要る。 同じホストの同じ辺に2つ結合すると同じ場所に重なる。先行するゲストの寸法を積算して辺に沿ってずらす。
  10. 10
    吸着で「内側＝入れ子」を無条件に優先すると、隣に置きたいのに入れ子になる。 隣に置こうとすると、たいてい別の泡の上を通過するため。縁の帯（約62px）は隣接、その内側が入れ子と分ける。
  11. 11
    吸着半径が広すぎると自由配置ができなくなる。 110px では空きに置いたつもりが必ずどこかに吸着した。62px＋辺方向の許容36px。触った感触で調整すべき値。
  12. 12
    拘束の段階を増やす前に、それが「操作」で表せないか疑う。 「開いた」を奥行き拘束（bind:"depth"）にしたせいで、隣にスナップした瞬間に opener のリンクバブルが消えるバグを出し、それを繕うために「拘束を外しても関係は残す」という仕組みまで足した。実際には「開く」という操作が初期配置を決めるだけでよく、拘束は最初から要らなかった。拘束は不変な関係にだけ与える。一度きりの出来事は操作で表す。
  13. 13
    隣接はホストの座標系に入れない。 中に入るのと隣に並ぶのは幾何的に別物。隣接でホストの縮尺を継承させると「リストの隣に、リストより手前でアイテムを大きく開く」が書けなくなる。隣接は画面空間で解き、ゲストの縮尺は自分の z から取る。
  14. 14
    帯の起点はその関係自身のアンカーから引く。 相手の現在の結合先アンカーを使うと、別の相手にスナップし直した瞬間に帯の根元が飛ぶ。
レンズに課す2つの制約

A. 矩形を矩形に写す。 位置と一様スケールだけを曲げ、中身は歪めない。回転・せん断・台形歪みは禁止。出力が translate + scale + opacity に収まるので、同じレンズが Canvas でも DOM でもそのまま動く。魚眼でも各泡は軸平行の矩形のまま。

B. 逆変換を必ず持つ。 scale は「その点における射影の局所倍率（ヤコビアンの対角）」と定義する。これで透視も魚眼も同じ式になり、unproject = 画面の移動量 ÷ 局所倍率 がタダで出る。逆変換のないレンズは「見るだけ」になり、掴めない。

// 透視：奥行き差 → 倍率
depthMag = dz => 1 / (1 + K_PERSP * dz)

// 魚眼：tanh の微分がそのまま局所倍率
mag = mag0 * sech²(u / K) * depthMag(dz)

1 − 0.1×layerIndex（現行）は layerIndex ≥ 10 で負になる。1/(1+k·dz) なら遠方で 0 に漸近するだけで、これが本来の透視の式。

09

残っている弱さ

プロトタイプを読み直して見つけた、まだ直していない／設計として決まっていない点。実装前に潰すべきものと、持ち越してよいものが混ざっている。

実装で必ず問題になる

  • 毎フレーム全解決している。 O(泡数 × 関係数) の走査が数か所ある。とくに chainDepth() は鎖を1本遡るごとに relations.find() で線形探索していて、軸に刺さると毎フレーム全泡ぶん走る。実装では to をキーにした関係索引とメモ化が要る。
  • 解決の順序に1フレームの遅れがある。 席の譲り合い → 箱の成長 → 隣接位置の算出、の順で走るため、隣接の位置は1フレーム古い箱サイズを見ている。目には見えないが、正しくは不動点まで回すか、依存順にトポロジカルに解くべき。
  • 帯の描画順が「相手の z のすぐ後ろ」に固定されている。 ホストと相手のあいだに無関係な泡が挟まると、帯がその泡を横切る。現行 LinkBubbleView も同じ制約を持つが、新設計では関係が増えるぶん目立つ可能性がある。

設計として決まっていない

  • アンカーの宣言者。 中身（React コンポーネント）が測って登録するか、宣言的に持つか。前者はレイアウトがコンテンツに依存して1フレーム遅れる。現行の BubbleRefsContext は前者。
  • 席の譲り合いは減衰付きの局所解法。 詰まった配置では収束が遅く、局所最適に落ちうる。実装で本当に必要な品質かは未検証。
  • 隣接の並び順が配列順に依存する。 引き剥がして付け直すと列の末尾へ回る。妥当な挙動だが暗黙。明示的な順序を持たせるべきか。
設計そのものへの疑い。 いちばん確信が持てていないのは次元を軸に刺すという操作の UI としての分かりやすさ。プロトタイプではドロップダウン3つで露出しているが、これは開発者向けの見せ方で、利用者にそのまま出すものではない。プリセット（現行 bubble-ui / 履歴を奥行きに / 世界線ビュー）のような名前のついた組み合わせが主で、軸の直接操作は裏口、という構成が現実的だと考えている。
10

次の一手

Canvas プロトタイプでの検証はここで一区切り。現行 bubble-ui の要素はすべて新しい概念に乗り、当初の「もっと自由な三次元」という要求も、軸の差し替えが1本の補間で繋がることで確かめられた。

実コードへ移すなら bublys-libs/bubble-space を nx g @nx/js:lib で生成し、3層 DDD に載せる。層の切り方はプロトタイプの構造がそのまま対応する。

層置くもの
domain/Bubble Relation Anchor Dimension Lens View。純粋な TypeScript、React も Redux もインポートしない
ui/解決済みの画面矩形リストを受け取って描くだけの表示層。Canvas と DOM の両方を差し替えられる（レンズの制約 A がこれを可能にする）
feature/Redux 連携、ドラッグと吸着、世界線との接続

Redux スライスは集約のリポジトリに徹する。Relation の追加・削除・拘束の解除といったロジックは、スライスの reducer ではなく集約のメソッドとして持たせる。
