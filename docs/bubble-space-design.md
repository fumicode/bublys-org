## 0. 何を根拠にしているか

出典を混ぜないために、主張の根拠を3種類に分けて表記する。

| 印 | 意味 |
|---|---|
| **実測** | この文書を書く過程で実際にコードを走らせて数値を取った。再現手順を併記する |
| **監査** | 6視点の自動監査が挙げ、検証役が「確認」と判定した。**ただし65件中の却下が0件**なので、追認寄りの可能性がある |
| **第1版** | 2026-09-10 の設計ノートで明示的に決めていたこと |

監査の内訳は 設計整合性10 / 正しさ10 / 操作12 / 視覚12 / API12 / 性能9 の計65件。
**却下0件という結果自体を信用しすぎないこと。** 実際、後述のとおり監査が「バグ」と呼んだもののうち
少なくとも1件は、第1版が意図して決めた仕様だった（監査エージェントは第1版を見ていない）。

## 1. 中心の公理は生きている

> 泡の画面上の見え方は、**論理座標 (x, y, z)** と**レンズ**の合成だけで決まる。
> それ以外の特別扱いを一切しない。

この公理は実装でも守られている。`resolveSpace()` は2経路（拘束する関係があればホストのアンカー、
なければ次元→軸→Vec3→レンズ）で合流し、描画順は**絶対 z の1回のソート**だけで決まる
（`domain/resolve.ts:216-222`）。第1版が狙った「孫が祖父より手前に出られる」も成立している。

壊れているのは公理ではない。**同じ量が2〜3箇所で別々に計算されている**という、たった1つの形が
繰り返し現れている。以降の多くはその系にすぎない。

## 2. 第1版の制約は実装でどうなったか

### 2.1 守られた

| # | 制約 | 実装 |
|---|---|---|
| 01 | 消失点は焦点と別に持つ | `lens.ts:31` `VANISHING = {dx:-130, dy:-165}` |
| 02 | 焦点より手前は透明にして消す | `lens.ts:37` `frontAlpha` |
| 05 | 穴は自前サイズの比率、席は絶対値 | `resolve.ts:133-135` は `host.ownSize` 基準 |
| 06 | ホストを押し広げるのは席だけ | `solve.ts:24-30` は `space.seats()` のみ走査 |
| 07 | ホスト自身の中身は自前サイズの範囲にだけ描く | `solve.ts:74` の `fixed` が `ownSize` |
| 08 | 左上より外へ出さない制約付きで最小移動。減衰 0.35 | `solve.ts:47-62`, `:101-102` |
| 09 | 隣接には辺に沿った並び順が要る | `resolve.ts:107-115` の `along` |
| 10 | 縁の帯は隣接、その内側が入れ子 | `magnet.ts:23` `EDGE_BAND = 62` |
| 11 | 吸着半径 62px＋辺方向の許容 36px | `magnet.ts:21`, `:80` |
| 12 | 拘束を増やす前に「操作」で表せないか疑う | `bind:"depth"` は導入されていない。`opened` は `bind:"none"` |
| 13 | 隣接はホストの座標系に入れない | `resolve.ts:97-128` はゲスト自身の `sp.scale` を使う |
| 14 | 帯の起点はその関係自身のアンカーから | `resolve.ts:196-203` |

**制約05 は監査の誤検出を1件生んだ。** 監査は「育った箱がアンカーに効かない」として、
`hole` 矩形が `measureBoxes` の結果ではなく `host.ownSize` を見ていることをバグとして挙げた。
しかし第1版はこれを明示的に決めている——

> 両方を比率にすると「成長 → 比率アンカー拡大 → 再衝突 → さらに成長」で発散する。
> 逆に穴を伸びた後のサイズの比率にすると、伸びた分だけ穴が広がって中身が破綻する。

`solve.ts:74` の `fixed` が `ownSize` なのも制約07 そのもの。**この指摘は棄却する。**
同じ指摘に含まれていた「`measureBoxes` の `passes=4` は席が5段以上ネストすると足りない」の
部分だけは有効だが、デモで到達する深さは1〜2なので優先度は低い。

### 2.2 ずれた

| # | 制約 | 第1版が言っていたこと | 実装 |
|---|---|---|---|
| 03 | 焦点の奥行きは**既定で**一番手前の泡に合わせる | **規則**（既定でそうなる） | 命令形の一発操作 `focusOnFront()` になった。結果、両デモが `setTimeout(focusOnFront, 0)` を書いている |
| — | 不変条件は**索引を張り直す `reindex()`** が担保する | **プロトタイプに実在した**（`bubble-lab.html:185-196`） | 移植で落ちた。`space.ts:19` は「`relate()` が担保する」に書き換わり、`fromPlain()` は無検証で素通し |
| B | `scale` は局所倍率（ヤコビアン）。`unproject = 画面の移動量 ÷ 局所倍率` がタダで出る | scale＝ヤコビアン | `fisheyeX` は `scale: max(m/mag0, 0.16)` と**正規化して**返す一方、y は `max(m, 0.12)` を使う。前提が崩れている |

**制約03 のずれが、API の写経を1つ生んでいる。** 「既定で最前面を追う」を規則として実装していれば、
`setTimeout(focusOnFront, 0)` は存在しない。第1版は規則として書いていたのに、実装が命令形にした。

**`reindex()` は設計上の願望ではなく、動いていたコードだった。** プロトタイプでは関係配列全体を
後ろから走査して「1つの泡に placed は高々1つ（新しい方を残す）」を正規化し、`bindingOf` 索引を
張り直していた——

```js
// bubble-lab.html:185-196
function reindex() {
  const seen = {};
  // 後ろにあるものほど新しい。新しい拘束を優先し、古い拘束は外す。
  for (let i = relations.length - 1; i >= 0; i--) {
    const r = relations[i];
    if (bindOf(r) === "none") continue;
    if (seen[r.to]) relations.splice(i, 1);   // 二重の placed 拘束は許さない
    else seen[r.to] = r;
  }
  bindingOf = seen;
}
```

**関係がどう入ってきたかに依存しない**のが要点で、だから外部からの復元でも不変条件が保てた。
実装はこれを `relate()` の中の事前ガードに置き換えたので、`relate()` を通らない入口
（`fromPlain()` ＝ 世界線からの復元）では不変条件が効かない。
**担保の位置が「状態の正規化」から「操作の前提条件」へ下がった。**

**制約B のずれが、掴めないレンズを1つ生んでいる。** 第1版の「÷ 局所倍率でタダで出る」という
近道は、`scale` が本当にヤコビアンであるときにしか成り立たない。`fisheyeX` は正規化して返すので
成り立たず、さらに `project` は `dzOf()` で量子化を通すのに `unproject` は生値を使う
（`lens.ts:76` vs `:89`）。

> **実測**（`focus.z` を変えて `p={x:0,y:100,z:0}` を往復させる, `quantize=true` 既定）
>
> | `focus.z` | y の往復 | 誤差 |
> |---|---|---|
> | 0 | 100 → 100.00 | 0.0% |
> | 0.4 | 100 → 89.60 | **10.4%** |
> | 0.5 | 100 → 87.00 | **13.0%** |
> | 1.3 | 100 → 89.46 | **10.5%** |
>
> `focus.z` が整数のときだけ誤差0。魚眼に切り替えて焦点を少しでもずらすと泡がカーソルから逃げる。

### 2.3 第1版が「未決」と明記していて、実装が暗黙に決めたもの

第1版の「残っている弱さ」に書かれていた論点は、**議論されないまま実装側の都合で片付いた**。
これらは第2版で決め直す（§4）。

| 論点 | 第1版 | 実装が選んだもの |
|---|---|---|
| `beside` の `gap` の尺度 | 「ホスト側の尺度や固定 px のほうが自然な場面もありそうで、**まだ決め切れていない**」 | ゲストの縮尺（`resolve.ts:102` `a.gap * sp.scale`） |
| 隣接の並び順 | 「配列順に依存する。**明示的な順序を持たせるべきか**」 | 配列順のまま。しかも後述のとおり再結合で必ず末尾へ飛ぶ |
| 席の譲り合いの品質 | 「局所最適に落ちうる。**実装で本当に必要な品質かは未検証**」 | 検証されないまま採用。§4.1 のとおり収束しない配置が実在する |
| アンカーの宣言者 | 「中身が測って登録するか、宣言的に持つか」 | 宣言的（呼び出し側が `hole()` を書く） |
| 軸に次元を刺す UI | 「開発者向けの見せ方。**プリセットが主で軸の直接操作は裏口**、が現実的」 | **裏口だけが出荷された**（次項） |

### 2.4 プリセットが落ちた — 正面玄関を作らずに裏口だけ出荷した

第1版は軸の直接操作について「これは開発者向けの見せ方で、利用者にそのまま出すものではない。
**プリセットのような名前のついた組み合わせが主で、軸の直接操作は裏口**、という構成が現実的」と
書いていた。そして**プロトタイプにはそのプリセットが実在した**。

```js
// bubble-lab.html:884-888
const PRESETS = {
  current:   { axes:{x:"free.x", y:"free.y",         z:"free.z"},        lens:"perspective", quantize:true  },
  histz:     { axes:{x:"none",   y:"history.branch", z:"history.age"},   lens:"perspective", quantize:false },
  worldline: { axes:{x:"history.index", y:"history.branch", z:"none"},   lens:"fisheyeX",    quantize:false },
  flat:      { ... },
};
```

ツールバーの1行目は「現行 bubble-ui / 履歴を奥行きに / 世界線ビュー / フラット」の4ボタンで、
押すと軸・レンズ・量子化・焦点がまとめて切り替わる。**これが第1版の言う「主」のUI。**

実装には**プリセットが1つも無い**。両デモが出しているのは軸のドロップダウン3つ＋レンズ1つ、
つまり第1版が「裏口」と呼んだものだけ。次元も減っている。

| | プロトタイプ | ライブラリ |
|---|---|---|
| プリセット | 4種 | **0** |
| 次元 | 10種 | 6種 |
| 落ちた次元 | — | `history.index`（履歴の世代）／`history.age`（履歴の古さ）／`history.branch`（履歴の枝）／兄弟の順序 |

落ちた4次元は**すべて履歴・世界線まわり**で、`worldline` と `histz` プリセットが使っていたもの。
つまり「同じ泡の集合が、軸を差し替えるだけで世界線ビューになる」という第1版の目玉の実証が、
実装では**再現できない**。第1版の移行対応表が `WorldLinesCanvasView.makeProjector` → `FisheyeLens` と
書いていた対応も、レンズだけ移って次元が来ていないので繋がっていない。

> **決めること**: プリセットを `View` の名前付き組み合わせとしてライブラリに持たせるか。
> 持たせるなら、履歴系の次元をどこが提供するか（bubble-space が世界線を知るのか、
> アプリが `registerDimension` で刺すのか）も併せて決まる。
> 現状 `registerDimension` は**リポジトリ全体で呼び出し0件**なので、拡張点として機能していない。

## 3. 第1版に無かった原則

監査で必要性が判明した、第1版が言及していなかった原則。**これらを足すことが第2版の主な仕事。**

### 原則 A — 同じ量は1箇所でだけ計算する

監査65件のうち、少なくとも12件がこの1つの違反に帰着する。

```
dz（含む＝手前に浮く量）の解釈が4箇所で3通り
   席の矩形      depthMag(dz)                  resolve.ts:136   生値
   実際の縮尺     depthMag(round(dz*2)/2)       resolve.ts:139   半整数丸め
   絶対 z         dz そのまま                   resolve.ts:149   生値
   箱の予約       depthMag(dz)                  solve.ts:27      生値
   → 既定 dz=-0.15 は quantize=true(既定) で縮尺だけ 0 に潰れ、箱は約4%大きいまま

「一番手前」が2通り
   frontLayer()  = min(free.z, 0)               space.ts:79   ← reduce 初期値0の原点バイアス
   frontZ        = min(解決済み z)               resolve.ts:226
   → open() は前者、focusOnFront は後者を使う

「画面 → 論理」が2経路
   ドラッグ      dx / placement.scale           useBubbleSpace.ts:109,158
   引き剥がし     lens.unproject(...)            useBubbleSpace.ts:221
   → perspective と flat では偶然一致するので気づかれない

「見えない」が3通り
   帯を捨てる    to.scale < 0.1                 resolve.ts:181
   泡を捨てる    opacity<0.03 || scale<0.02     BubbleSpaceView.tsx:57
   帯を捨てる    2px 未満                       resolve.ts:208
```

`anchorIsOutside()` と `isLink()` は **定義されているのにリポジトリ全体で一度も呼ばれず**、
`resolve.ts:97` と `:196` が生の `kind` 比較でそれを書き直している。
語彙を作った後、実装がそこへ寄っていない。

> **この原則の実装形**: `effectiveDz(dz, view)` / `frontZ(space)` / `isTangible(placement)` を
> domain に各1本置き、`resolve` / `solve` / `magnet` / `view` が全部そこを通る。

### 原則 B — 奥行きは両側に効く

`frontAlpha(dz)` は `dz < 0` のときしか 1 を割らない（`lens.ts:37`）。つまり**焦点より奥の泡は
`dz=1` でも `dz=20` でも `opacity` が 1**。奥行きの手がかりが `scale` 1本しかないので、
画面は「大きさの違う同じ鮮やかさの板が並んだもの」になる。デモはどちらも中身が白パッドなので
特に平板に見える。

第1版は制約02 で**手前側の発散**だけを扱い、**奥側の減衰**を原則として立てていなかった。

> レンズの出力に `haze` を足し、`project` が返す。`flat` は 0 を返す（平行投影が平板なのは正しい）。

### 原則 C — 器は観測者の道具であって、泡の一部ではない

`transform: scale(p.scale)` が泡ごと全部に掛かるので、中身だけでなく**掴む・読むための部品**も
同率で縮む。

| 奥行き | 縮尺 | ヘッダ24px | タイトル12px | 枠1px |
|---|---|---|---|---|
| `dz=3` | 0.562 | 13.5px | 6.7px | 0.56px |
| `dz=6` | 0.390 | 9.4px | 4.7px | 0.39px |

ドラッグは**ヘッダからしか始まらない**設計（`BubbleSpaceView.tsx:25`）なので、奥の泡は掴めもしない。
hotel デモは `open()` のたびに `frontLayer()-1` で面を1枚掘るため、パネル4枚で主役の勤務表が
この状態になる。

> **中身は遠ざかる。把手は遠ざからない。読めなくなったら中身は描かない。**
> 「中身は遠いから小さい」は正しいが、「把手も遠いから小さい」は物理の誤用。
> 窓や取っ手はスケール模型の一部ではなく、観測者の道具。

### 原則 D — 予告は本番と同じ規則を通る

`findMagnet()` が描く予告枠と、実際の着地点が別の計算になっている。

- **contains**: 予告はカーソル位置に `seat(lx,ly)` を描く（`magnet.ts:60-66`）。しかし着地後は
  `settleSeats` の `fixed` に必ずホスト自身の中身矩形が入り（`solve.ts:74`）、`share=1` で
  押し出される（`solve.ts:93`）。**ホストの真ん中に落とすと、予告は真ん中に出て、実際は右か下へ滑る。**
- **adjacent**: 予告は常に先頭スロット（`magnet.ts:84-87`）だが、`resolve` の `beside` は同じ辺の
  先客の分だけ `along` をずらす（`resolve.ts:107-115`）。**先客が1つでもあると丸ごと1枠ぶんズレる。**

着地の挙動そのものは第1版の設計どおり（「ホスト自身の中身も場所を取るものの一つ」が
"放り込まれた泡がホストの中身を隠さない" を特別扱いなしに満たす）。**問題は着地ではなく、
予告が規則の外にあること。**

> 予告は `resolveSpace` に仮の関係を通した結果を描く。予告専用の計算を持たない。

### 原則 E — 連続入力は補間しない

CSS トランジション `.26s` は `dragging` のときだけ切られる（`BubbleSpaceView.tsx:173`）。
しかし連続入力はドラッグだけではない。`settleSeats` は毎フレーム席を動かし、`onWheel` は
毎イベント `focus.z` を動かす。どちらも毎フレーム「260ms かけてそこへ行く」を再設定するので、
入力と絵がずれて空間が重い液体に見える。`width`/`height` にも掛かっているのでレイアウトも遅れる。

> 連続入力＝補間しない／離散イベント（レンズ切替・軸切替・open・focusOn）＝補間する。

### 原則 F — 収束が保証できないものを状態にしてはいけない

§4.1 で詳述。**第2版で最も重要な決定。**

## 4. 決めるべき論点

### 4.1 席の譲り合いは「記録すべき配置」か「解けば再現できる見え方」か

**第2版で最初に決めるべき論点。** これ1つで4つの不具合が同時に消える。

現状は**例外**になっている。中心の公理は「泡は座標を持たず、画面位置は `resolveSpace` が解く」
なのに、席の位置だけは `settleSeats` が毎フレーム `moveSeat()` で `Space` に書き戻す
（`solve.ts:104`）。箱の大きさは `measureBoxes` で毎回解き直すのに、席の位置は解かずに持つ、という非対称。

**収束は保証されていない。** 停止条件は「1つでも席が 0.05px 超動いたか」だけで、単調減少する
エネルギーも反復上限もない（`solve.ts:103`）。

> **実測**（`solve.ts` を忠実に移植し、ランダム配置を1件あたり最大3000フレーム回す）
>
> | 条件 | 収束しない | 収束フレーム数 |
> |---|---|---|
> | 席1〜4・hole 無し | **0 / 20000 (0%)** | 最悪 97 |
> | 席2〜8・hole 0〜2枚 | **128 / 20000 (0.64%)** | 収束したものは最悪 199 超 |
>
> 反例（席2〜8）: ホスト 312×165 に席8つ。2000フレーム後も席が毎フレーム
> `(0,-8.33)` と `(0,+5.39)` 動き続ける**リミットサイクル**。押し合う2席が永久に振動する。
>
> 監査側も独立に同じ現象を観測している（4000構成中12件が停止せず、収束しても最悪349反復・平均29.9反復）。
> 条件次第で率は変わるが、**現象そのものは再現する**。

**この1つが引き起こしている連鎖:**

```
settleSeats が収束しない
  → RAF effect が space を依存に持つので毎フレーム再発火し、止まらない
      （useBubbleSpace.ts:69-75）
  → useSpaceWorldLine の 350ms タイマーが毎レンダー張り直され、一度も満了しない
      （useSpaceWorldLine.ts:61 / scope が毎レンダー別物なのも重なる → §5)
  → 配置が世界線に記録されない
  → 「配置も世界線に載っている」というデモの主張が、その配置では成り立たない

settleSeats が Space を書き換える
  → resolved も children も毎フレーム作り直される
  → ドロップ1回でアプリ全体が平均30・最悪349フレーム再構築される
  → 希望位置（ユーザが手で置いた場所）が譲り合いの結果で上書きされ、戻す術がない
```

**決める必要があるのは1文。** 選択肢は2つ。

- **(a) 解にする** — `seat` は**希望位置**だけを持ち、重なり解消は `resolveSpace` と同じく毎回の解として
  `Placement` 側に出す。書き戻さないので収束も debounce も不要になり、上の連鎖が丸ごと消える。
  中心の公理とも一致する。代償は、解を毎回計算するコストと、`Placement` に「希望と実際」の2つが載ること。
- **(b) 状態のままにする** — `settleSeats` が**収束判定を返し**、不動点に達したときだけ1回書き戻す。
  リミットサイクルを検出したら反復上限で打ち切る。debounce は不要になるが、公理の例外は残る。

第1版の哲学（「シンプルなルールで自然な動作」）に照らすと **(a)** が素直だが、
`Placement` の設計が変わるので影響範囲は大きい。**ここを議論する。**

### 4.2 量子化は「見え方」か「モデルの量」か

`view.quantize` は `View` に属する（`view.ts:10`）ので**見え方のはず**なのに、実際には配置の意味を
書き換えている。

- 既定 `dz=-0.15` の「含むと少し手前に浮く」が `round(-0.3)/2 = 0` で**消える**
- しかも箱の予約とアンカー矩形は生値のままなので、約4%のズレが残る
- **投げ込み先まで変わる**: 親の中に子が座っている状態で子の上にドラッグすると、`quantize=true` では
  子の縮尺が親と同じになってタイ→配列順で親が勝ち、`quantize` を切ると子が 1.0406 倍になって子が勝つ。
  「Z量子化」ボタンを押すだけで落ちる先が変わる（`magnet.ts:45`, `resolve.ts:139`）

> **決めること**: 量子化をレンズの中に閉じ込めて配置の意味に触れさせないか、
> あるいはモデルの量として `View` から `Space` 側へ移すか。中途半端が一番悪い。

### 4.3 アンカーは3種か、2属性か

`hole` / `seat` / `beside` は1つの列挙だが、実際に分岐を決めているのは独立した2述語で、
その名前は既に `anchor.ts` に書かれている。

```
                      ホストの座標系に入る      画面上の接触
  ホストが大きさを決める     hole                  （空き）
  ゲストが大きさを決める     seat                  beside
```

3種は「大きさを誰が決めるか × 座標系に入るか」の2×2のうち**3マスを埋めているだけ**で、
4マス目「外側でホストが大きさを決める」は表現できない。
`anchorIsOutside()`（4マス目を判定する述語）は定義だけされて未使用。

また `bind` の2値（`placed` / `none`）も、`placed` に「ホストの世界に入る」と
「画面上で辺が接するだけ」の2つの意味が同居している。`beside` は `placed` なのにホストの縮尺も
z も継承せず、`free.x`/`free.y` は無視されるのに `free.z` だけ効く、という半端な状態になっている。

> **決めること**: 2属性に開くか、3種のままで述語（`anchorSizesGuest` / `anchorIsOutside`）を
> 実際に使って判定の定義を1箇所にするか。4マス目に用途があるかも併せて。

### 4.4 第1版が明示的に未決としていた2つ

- **`beside` の `gap` の尺度** — 現状ゲストの縮尺（奥へ行くとすき間も縮む: 14px → 8px）。
  第1版は「ホスト側の尺度や固定 px のほうが自然な場面もありそう」と書いている。
  加えて監査は「`beside` は『辺が接する』と説明しているのに実際は 14px 空いていて、
  膜（seam）も引かれていない」と指摘している。**説明と絵が食い違っている。**
- **隣接の並び順** — 配列順のまま。しかも `relate()` は `placed` の場合、先に `release()` で
  既存を消してから `found` を探すので、**「繋ぎ直す」分岐は placed では到達不能**
  （`space.ts:128-134`）。毎回末尾に push されるため、**一度剥がして付け直すと必ず列の末尾へ飛ぶ**。
  第1版は「妥当な挙動だが暗黙」と書いていたが、実装は「妥当」ですらない挙動になっている。

### 4.5 器（ヘッダ・取っ手）は泡のものか、画面のものか

原則C。決めれば「奥の泡が掴めない」「選択の印が奥で消える」「LOD が無い」が同時に片付く。

## 5. 記録 — 検証済みのバグ（今回は直さない）

いずれも自分で数値を確認済み。§4 の議論とは独立に壊れている。

### 5.1 魚眼レンズの逆関数が `project` と違う丸めを使う

`domain/lens.ts:89`（`project` 側は `:76`）。`project` は `dzOf()` で量子化を通すのに、
`unproject` は `z - ctx.focus.z` の生値。**実測で誤差10.4〜13.0%**（§2.2 の表）。
`lens.ts:17-18` が「逆変換 `unproject` を必ず持つ」とレンズの契約として宣言している当のものが破れている。

> **直し方**: `unproject` 側も `dzOf(z, ctx)` を通す（`ctx` は既に受け取っているので1行）。
> `LENSES` 総当たりで `unproject(project(p)) ≈ p` を確かめる spec を置けば契約がテストとして固定される。

### 5.2 画面に描かれていない泡にマグネットが吸い付く

`domain/magnet.ts:51`（描画側の判定は `ui/BubbleSpaceView.tsx:57`）。
足切りが `hp.scale < 0.25` だけで `opacity` を見ない。

> **実測**
>
> | `dz` | `depthMag` | `frontAlpha` | 描画 | マグネット候補 |
> |---|---|---|---|---|
> | -1.5 | 1.639 | 0.175 | される | なる |
> | **-1.82** | **1.898** | **0.000** | **されない** | **なる** |
> | **-2** | **1.900** | **0.000** | **されない** | **なる** |
> | **-3** | **1.900** | **0.000** | **されない** | **なる** |
> | -5 | 0.040 | 0.000 | されない | ならない |
>
> `frontAlpha` は `dz ≤ -1.82` で 0 になるのに、`depthMag` は `MAG_MAX = 1.9` にクランプされるので
> `scale = 1.9` で足切りを通過する。**画面に何も無いところに吸い付く。**

> **直し方**: 原則A の `isTangible(placement)` を1本置き、描画・マグネット・ヒットテストが同じものを読む。

### 5.3 世界線の debounce がレンダーに張り付いて発火しない

`feature/useSpaceWorldLine.ts:61`。記録用 effect の依存に `scope` が入っているが、
`useCasScope` は **`useMemo` で包まれていない素のオブジェクトリテラルを返す**
（`bublys-libs/world-line-graph/src/lib/feature/useCasScope.ts:500-518` で確認）。
よって `scope` は毎レンダー別物になり、effect が毎レンダー再実行され、350ms の `setTimeout` が
`clear` → 再設定され続ける。settle 中やドラッグ中は16msごとに再レンダーされるのでタイマーが満了しない。
ついでに `spaceFingerprint`（`space` 全体の `JSON.stringify`）も毎レンダー走る。

> **直し方**: 応急処置は `scope` を ref に逃がして依存を `[space]` だけにする（数行）。
> 根本は §4.1 で席を書き戻さなくすること。そうすればこの駆け引き自体が消える。
> なお `useCasScope` が毎レンダー新しい参照を返すのは **bubble-space だけの問題ではない**ので、
> あちら側を `useMemo` で包むかどうかは別途判断が要る。

## 6. 実装再開の前に

第1版は「設計確定・実装未着手」で終わっていた。第2版は**未決の論点を決め切ってから**実装に戻る。
決める順序は依存関係で決まる。

```
4.1 席は状態か解か  ←── ここが決まらないと Placement の形が決まらない
      │
      ├─→ 4.2 量子化は見え方かモデルの量か   ←── 決まらないと dz の単一定義が書けない
      │         │
      │         └─→ 原則A（同じ量は1箇所で）  ←── dz / frontZ / 可視性 / 画面→論理
      │                    │
      │                    ├─→ 5.1 5.2 5.3 のバグはここに吸収される
      │                    └─→ 原則D（予告は本番と同じ規則を通る）
      │
      └─→ 4.3 アンカーは3種か2属性か  ←── resolve の分岐の書き方が変わる

原則B（奥行きは両側に効く）      ── 独立。先に入れても損をしない
原則C（器は観測者の道具）         ── 独立。4.5 を決めれば入る
原則E（連続入力は補間しない）      ── 独立
```

**原則B・C・E は他と独立**なので、議論を待たずに入れても後で直しにならない。
見た目の変化が一番早く出るのもここ。

テストは0件のまま（`vite.config.mts` と `tsconfig.spec.json` は揃っていて `README` も
`nx test bubble-space` を案内しているが、`src` 配下に `*.test.ts` が1つも無い）。
このモデルは純関数の塊なので、決めた原則をそのまま命題として書き下せる。
**「ルールの宣言」としてのテストが、第2版の成果物の一部**になる。
