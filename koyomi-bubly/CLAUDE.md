# koyomi-bubly（暦バブリ）— 開発者ガイド

**日付について暦が言えることを受け持つバブリ。** いまは六曜だけ（#235）。祝日などは入れていない。

ほかのバブリ（シフトントンなど）の日付に六曜を添えるための部品で、単体でも月のカレンダーとして使える。

---

## 構成

```
koyomi-bubly/
  koyomi-model/   # 暦のモデル（純粋 TypeScript。React も Redux も使わない）
  koyomi-libs/    # バブルの部品とルート（React）
  koyomi-app/     # 単体で開く画面（dev: http://localhost:4210）と bubly.js の出力
  tools/          # 旧暦の表を作るスクリプト
```

依存の向きは model ← libs ← app。**model はほかのバブリの型に依存しない**（素の年月日 `CalendarDate` を受け取る）。
どのバブリからも使えるようにするため。

---

## 六曜の決まり

- 六曜は旧暦から決まる：（旧暦の月＋旧暦の日）を 6 で割った余り。0 大安・1 赤口・2 先勝・3 友引・4 先負・5 仏滅。
  閏月は同じ番号の月として数える（`rokuyo.ts`）
- 旧暦は天保暦の決まりの太陰太陽暦（`kyureki.ts`）
  - 朔（新月）を含む日（日本時間）がその月の1日
  - 中気を含む月に、その中気の月番号を付ける（冬至を含む月が11月）。中気を含まない月は閏月
- **旧暦は表で持つ**（`kyurekiMonths.ts`）。範囲は **2020〜2032年**。範囲外の日は旧暦も六曜も `undefined`
  - 2033〜2034年は上の決まりだけでは月が決まらない（2033年問題）。決め方が定まってから表を伸ばす。
    スクリプトは 2033年以降を作ろうとすると止まる

## 旧暦の表を作り直す

`kyurekiMonths.ts` は生成物なので手で直さない。`kyurekiMonths.staleness.test.ts` がスクリプトとの食い違いを見張る。

```bash
node koyomi-bubly/tools/generate-kyureki.mjs 2020 2032 > koyomi-bubly/koyomi-model/src/lib/kyurekiMonths.ts
```

- 天文計算は Meeus『Astronomical Algorithms』（朔：第49章、太陽の視黄経：第25章の低精度版）
- 太陽の黄経の誤差は時刻で15分程度あるので、**日本時間の0時の前後30分に来た朔・中気は標準エラー出力に出る**。
  出たものは公表値と照らして確かめる
  - 朔：国立天文台の暦要項（公表は翌年分まで）か、NASA の月の位相の表（Espenak、2001〜2100年、UT）
  - 中気：その日付が前後1日ずれても同じ旧暦の月に収まるなら、表には影響しない
- 2020〜2032年の表を作ったときに確かめたこと（テストにも入れてある）
  - 朔が0時の近くに来た3件（2028-01-27 00:12・2029-12-05 23:52・2032-07-07 23:41）は、NASA の表と分単位で一致
  - 閏月：2020年閏4月・2023年閏2月・2025年閏6月・2028年閏5月・2031年閏3月
  - 2028年の旧正月は1月27日（中国の春節は時差で1月26日）
  - 2026年元日は大安

## ほかのバブリから使う

- バブリ同士をつなぐ「口」（`docs/bubly-composition.md`）はまだ無い。当面、使う側が `@bublys-org/koyomi-model` を
  直接 import する（名指しが残る。口ができたら置き換える）
- **使う側の bubly.js には koyomi-model を同梱する。** bubly.js のビルドは自分の libs 以外の `@bublys-org/*` を外部化し、
  OS が `window.__BUBLYS_SHARED__` で渡す前提になっている。OS は koyomi-model を持っていないので、外部化すると
  OS に読み込んだときに六曜が引けない（`vite.config.bubly.ts` の `external` で false を返す）
